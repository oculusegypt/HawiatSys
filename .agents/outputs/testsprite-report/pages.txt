2 Key Findings
Test Summary
The executable subset of the frontend suite is broadly healthy: most user flows, routing, SEO discovery, Arabic/RTL
rendering, and content navigation passed. Excluding 6 Blocked tests from the denominator, the run shows 60 passed
and 9 failed, for an 87% success rate. That indicates solid core functionality, but several user-facing gaps remain in
public-page metadata and a few key contact/help flows. The 6 Blocked cases were caused by the test environment’s
lack of mobile viewport control, so they do not reflect product defects, but they do limit coverage of responsive
behavior.
What could be better
The biggest quality gaps are in SEO/head metadata and a few content flow expectations. Several public pages are
missing `<title>`, `meta name="description"`, canonical, and Open Graph/Twitter tags, and one test found the homepage
H1 text does not match the visible hero headline. Two contact/request flows also failed to preserve or surface context:
Arabic submission values were not shown on the confirmation screen, and the urgent/scheduled request forms did not
visibly prefill the expected urgent context or datetime. The FAQ search also returned no match for a realistic Arabic
query. These issues affect discoverability, verification, and conversion.
Recommendations
Prioritize fixing the shared public-page head template first: add page-specific `<title>`, description, canonical, Open
Graph/Twitter metadata, and ensure the visible hero headline and H1 are aligned. Next, inspect the request-form
confirmation and prefill logic so submitted Arabic values remain visible after submit, urgent requests clearly carry their
context, and scheduled booking includes a real default datetime value. Then improve FAQ search relevance for Arabic
queries like "الحاوية أختار كيف". After each change, rerun the named tests in the suite to confirm the affected flows now pass;
the detailed, copy-ready fix list is below.

The submission succeeds, but the confirmation page is not displaying the saved form data. On the hosting side this
usually means the POST data is either not being persisted correctly or is being lost during the redirect/confirmation
render. Common causes include a mismatch between frontend field names and backend column names, a server-side
encoding issue causing Arabic strings to be dropped, a database collation/charset problem, or the confirmation page
being a static success screen that does not rehydrate the submitted values from the saved record.
Fix

stores and returns the submitted fields correctly, and that the confirmation page is populated from the submitted
payload rather than a static success message. Specifically, verify database/schema field mappings for Arabic text,
request parsing/encoding (UTF-8), and any sanitization or localization layer that may be dropping non-Latin input. If the

Cause
The blog listing likely uses non-unique or ambiguous markup for the article CTA, such as multiple overlapping anchors,
nested clickable containers, or links generated/obscured by CSS/JavaScript in a way that makes the visible "المزيد اقرأ"
text not correspond to a uniquely targetable anchor. As a result, the automation can see the text but cannot reliably map
it to a specific clickable element among many anchors, especially if the page structure lacks stable selectors or the link
is only accessible via hover/overlay/script behavior.
Fix
Make each blog card’s "المزيد اقرأ" control a unique, semantically identifiable link/button in the DOM. For example: wrap
each card action in a single <a> with a stable href to the article page, and add clear attributes such as aria-label, data-
testid, or a specific class. Avoid relying on duplicated generic anchors, nested clickable overlays, or content rendered
only through JS without distinct DOM targets. Ensure the article link is present in the initial rendered HTML (or hydrated
predictably) so automation can locate and click the first article consistently.

Cause
The hosting/application likely has a navigation or routing bug that inserts an about:blank state into the browser history,
or replaces the current document with an empty page during a transition. This can happen if the site is implemented as
an SPA without correct history handling, if a redirect/unload script targets about:blank, or if the server returns an
empty/placeholder document for one of the history URLs. As a result, the browser Forward button lands on an empty
DOM rather than the expected page, preventing verification of Arabic rendering.
Fix
Avoid forcing any route or redirect to about:blank/empty HTML during navigation, and ensure every page is served as a
real history entry with proper HTTP URLs and server-side routes. Check for scripts that call window.open('about:blank'),
location.replace('about:blank'), document.write(''), or similar patterns on navigation/unload; remove them. Also make sure
the site supports proper back/forward cache behavior and that SPA routing uses clean URLs with server fallbacks for
direct and history navigation, so the browser Forward button can restore the expected Arabic-rendered page instead of
an empty document.
