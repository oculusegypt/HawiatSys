BLOCKER 2 — PHP Other Revenue Idempotency
المشكلة الحالية

في PHP/Hostinger:

عند تكرار نفس عملية other_revenue:

لا يتم إنشاء Financial Transaction ثانية

وهذا جيد.

لكن:

يتم إنشاء Draft Record جديد

وهذا غير صحيح.

المطلوب أن يكون السلوك:

First Request
    ↓
Create Other Revenue
    ↓
Post Financial Transaction
    ↓
Return ID

Same Request + Same Idempotency Key
    ↓
Return Existing Record
    ↓
idempotent = true
    ↓
NO new draft
    ↓
NO new financial transaction
    ↓
NO new journal entry
يجب منع كل أنواع التكرار:
duplicate business record
duplicate draft
duplicate financial transaction
duplicate journal
duplicate allocation

ويجب أن تكون النتيجة:

{
  "idempotent": true
}

مع إعادة نفس السجل السابق.

اختبر على Hostinger الحقيقي وليس SQLite المحلي فقط.

BLOCKER 3 — Financial Period Lock HTTP Status
المشكلة الحالية

منطق قفل الفترة يعمل:

Posting after period closure
→ mutation rejected
→ financial totals unchanged

وهذا PASS وظيفياً.

لكن Hostinger يعيد:

HTTP 500

بدلاً من استجابة رفض مالية صحيحة.

المطلوب:

Closed Financial Period
+
Attempt Posting
=
HTTP 422

أو status مناسب ومقصود لرفض العملية، وليس 500.

مهم جداً

لا تغير منطق القفل نفسه.

القفل يعمل بالفعل.

المطلوب فقط:

معالجة الاستثناء بشكل صحيح.
إرجاع HTTP status مناسب.
رسالة خطأ واضحة.
عدم حدوث أي mutation.
عدم إنشاء Financial Transaction.
عدم إنشاء Journal Entry.

مثال متوقع:

{
  "error": "FINANCIAL_PERIOD_CLOSED",
  "message": "Cannot post financial transaction into a closed period."
}
