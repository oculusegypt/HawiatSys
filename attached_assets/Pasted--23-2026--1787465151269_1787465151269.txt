# تقرير التدقيق الشامل لدورة القيم المالية

**تاريخ التدقيق:** 23 أغسطس 2026  
**النطاق:** العقود، الفواتير، التحصيل، التوزيعات، الإيداعات، المرتجعات، المصروفات، الرواتب، العمولات، الأستاذ المالي، التقارير، واجهة الإدارة، ونسخة Hostinger/PHP.

## 1. الخلاصة التنفيذية

النظام يحتوي على بنية مالية جيدة مبدئيًا، تشمل:

- دورة حالات مالية: مسودة، بانتظار الاعتماد، معتمد، مرحّل، مرفوض، ملغى.
- توزيع دفعة واحدة على عدة عقود.
- إنشاء قيد أستاذ للتحصيل.
- حماية أولية من تكرار العملية.
- ربط الإيداعات بالسدادات.
- سجل تدقيق.
- نسخة Node ونسخة PHP للعمل على Hostinger.

لكن لا يمكن اعتبار الأرقام المالية حاليًا موثوقة محاسبيًا بشكل كامل، بسبب وجود مشاكل جوهرية في:

1. احتساب الحركات غير المرحّلة والملغاة ضمن الإجماليات.
2. احتمال احتساب نفس التحصيل مرتين عند وجود `receipt` و`payment`.
3. عدم ثبات علاقة الإيداع مع جميع توزيعات السداد.
4. اختلاف معالجة الضريبة بين العقد والفاتورة.
5. وجود مسارات عامة للسداد تتجاوز بعض ضوابط الرصيد والتوزيع.
6. إمكانية إنشاء أكثر من عملية بنفس مفتاح التكرار في ظروف التزامن.
7. اعتماد واسع على JSON وأرقام المستندات بدل علاقات مالية مضمونة في قاعدة البيانات.
8. وجود اختلافات بين Node وPHP في بعض تفاصيل الأستاذ والقيم.
9. تقارير تعرض أرقامًا تقريبية أو غير مكتملة، رغم أن واجهتها توحي بأنها تقارير مالية نهائية.

# 2. المشاكل الحرجة

## C-01 — الإجماليات تحتسب الحركات غير المرحّلة

**درجة الخطورة: حرجة**

في API يتم اختيار الحركات المالية باستبعاد السجلات المؤرشفة فقط، وليس باشتراط الحالة `posted`.

في مسار ملخص النظام، يتم احتساب:

- `payment`
- `receipt`
- `deposit`
- `bank_deposit`
- المصروفات
- المرتجعات

حتى لو كانت حالتها:

- `draft`
- `pending_approval`
- `approved`
- `rejected`
- `cancelled`

المواضع الرئيسية:

- `artifacts/api-server/src/routes/containerSystem.ts`
- حساب `paymentsByContract`
- حساب `expenses`
- حساب `maintenanceCost`
- حساب `debt`
- حساب كشوف العقود

وفي الواجهة:

- `FinancialCycleWorkspace.tsx`
- `ContainerSystemSpecialPages.tsx`

الواجهة تستخدم تقريبًا:

```ts
record.status !== "archived"
```

بدل:

```ts
record.status === "posted"
```

### الأثر

قد يظهر في المركز المالي:

- تحصيل مسودة قبل اعتماده.
- إيداع مرفوض.
- مرتجع ملغى.
- مصروف بانتظار الاعتماد.
- دفعة تم إلغاؤها، لكنها ما زالت داخلة في الرصيد.

### المطلوب

تعريف دالة موحّدة مثل:

```ts
isPostedFinancialRecord(record)
```

واستخدامها في:

- المركز المالي.
- كشف العقود.
- كشف العميل.
- التقارير.
- المطابقة البنكية.
- حساب المرتجعات.
- حساب الذمم.

## C-02 — احتمال احتساب التحصيل مرتين بين `receipt` و`payment`

**درجة الخطورة: حرجة**

النظام يعامل كلًا من:

```ts
receipt
payment
```

على أنه تحصيل مستقل.

في الواجهة:

```ts
const payments = scoped.filter(
  record => record.kind === "payment" || record.kind === "receipt"
)
```

وفي دورة المطابقة:

```ts
const receipts = active
  .filter(record => ["receipt", "payment"].includes(record.kind))
  .reduce(...)
```

وفي API كذلك يتم جمع النوعين معًا.

### دليل من البيانات

في النسخ المالية السابقة توجد أمثلة مشابهة:

- سند قبض بمبلغ **3000 ريال**.
- حركة دفع بمبلغ **3000 ريال** لنفس العميل والعقد.
- إيداع بنكي بمبلغ **3875 ريال**.

بالتالي قد يظهر التحصيل كالتالي:

- سندات القبض: 3875
- السدادات: 4000
- إجمالي ما تعتبره الواجهة تحصيلًا: 7875 تقريبًا
- بينما الإيداع الفعلي: 3875

وهذا يؤدي إلى فرق وهمي أو تضخيم للتحصيل.

### سبب المشكلة

لا توجد قاعدة واضحة تحدد هل:

- `receipt` هو المستند المالي الأساسي.
- `payment` هو المستند المالي الأساسي.
- أحدهما مجرد نسخة تشغيلية من الآخر.
- يجب ربطهما بعلاقة `sourcePaymentId` أو `sourceReceiptId`.

### المطلوب

اختيار نموذج واحد:

### الخيار الأفضل

اعتبار `payment` حركة التحصيل الأساسية، واعتبار `receipt` مستند عرض/طباعة مرتبط بها:

```text
payment
 └── receipt
```

ثم لا يتم جمعهما معًا في الإجماليات.

أو جعل `receipt` هو الحركة الأساسية وإلغاء احتساب `payment` عند وجود السند المرتبط.

## C-03 — إلغاء حركة مرحّلة لا ينشئ قيدًا عكسيًا

**درجة الخطورة: حرجة**

عند تغيير حركة مالية من `posted` إلى `cancelled`:

- يتم تحديث حالة الحركة.
- يتم إنشاء سجل تدقيق.
- لكن قيد الأستاذ السابق يبقى بحالة `posted`.
- لا يتم إنشاء حركة عكسية.
- بعض التقارير تواصل احتساب الحركة الأصلية.

الموضع:

`artifacts/api-server/src/routes/containerSystem.ts`  
ضمن PATCH للحركات المالية.

### الأثر

يمكن أن تصبح البيانات كالتالي:

```text
payment: cancelled
ledger_entry: posted
```

وهذا يعني أن المستند ملغى، لكن أثره المحاسبي لا يزال قائمًا.

### المطلوب

منع الإلغاء الصامت للحركة المرحّلة، واستبداله بأحد الخيارين:

1. إنشاء قيد عكسي موثق.
2. إنشاء حركة `reversal` مرتبطة بالمستند الأصلي.

مثال:

```text
payment 1000 credit
payment_reversal 1000 debit
```

ويجب أن تتضمن الحركة العكسية:

- `originalRecordId`
- `originalLedgerId`
- سبب الإلغاء.
- المستخدم المعتمد.
- التاريخ.
- مرجع التصحيح.

## C-04 — الإيداع متعدد العقود يحفظ العلاقة مع العقد الأول فقط

**درجة الخطورة: عالية**

في مسار التسوية، يمكن توزيع دفعة على أكثر من عقد:

```ts
allocations: [
  { contractId: 1, amount: 500 },
  { contractId: 2, amount: 700 }
]
```

لكن عند تحديث الإيداع، يتم حفظ:

```ts
linkedContractId: first.contract.id
linkedPaymentId: payment.id
```

أي أن الإيداع يحتفظ بعلاقة مباشرة مع أول عقد فقط.

الموضع:

`artifacts/api-server/src/routes/containerSystem.ts`  
ضمن مسار:

```text
/admin/container-system/financial/settle
```

### الأثر

- لا يظهر الإيداع كاملًا في كشف العقد الثاني.
- يصعب إثبات توزيع الإيداع.
- تقارير المطابقة البنكية لا تستطيع توزيع الإيداع على كل العقود.
- تفقد العلاقة الرسمية بين الإيداع والتوزيعات المتعددة.

### مشكلة إضافية

كود حساب الإيداعات في Node يبحث عن:

```ts
sourcePaymentId
```

بينما مسار التسوية يكتب:

```ts
linkedPaymentId
```

وهذا اختلاف مباشر يجعل الإيداع المرتبط لا يظهر في بعض كشوف العقود.

### المطلوب

اعتماد جدول أو سجل توزيع مستقل:

```text
payment_allocations
- paymentId
- contractId
- invoiceId
- amount
```

وإذا لم تتم الهجرة الآن، فيجب على الأقل:

- استخدام نفس اسم العلاقة في Node وPHP.
- قراءة `linkedPaymentId` و`sourcePaymentId` مؤقتًا للتوافق.
- حفظ `allocations` داخل الإيداع أو ربطه بالسداد فقط، ثم استخراج التوزيع من السداد.

# 3. مشاكل الفواتير والضريبة

## H-01 — الفاتورة لا تعالج `taxInclusive` مثل العقد

**درجة الخطورة: عالية**

العقد يعالج الحالة التي تكون فيها القيمة شاملة الضريبة:

```ts
total = amount
taxAmount = amount - amount / (1 + taxRate / 100)
amount = amount - taxAmount
```

لكن الفاتورة تقوم دائمًا تقريبًا بـ:

```ts
taxAmount = amount * taxRate / 100
total = amount + taxAmount
```

حتى إذا كان `taxInclusive = true`.

### مثال

إذا أدخل المستخدم فاتورة بقيمة شاملة الضريبة:

```text
amount = 1150
taxRate = 15%
```

المفترض:

```text
الصافي = 1000
الضريبة = 150
الإجمالي = 1150
```

لكن التنفيذ الحالي قد ينتج:

```text
الصافي = 1150
الضريبة = 172.50
الإجمالي = 1322.50
```

### المواضع

- `normalizeInvoicePayload` في Node.
- `hsNormalizeFinancial` في PHP.
- نموذج الفاتورة وواجهات الإدخال.

### المطلوب

توحيد تعريف:

- `subtotal`
- `taxAmount`
- `total`
- `taxInclusive`
- `taxRate`

مع تطبيق نفس المعادلة في Node وPHP.

---

## H-02 — تعريف `amount` غير ثابت بين المستندات

**درجة الخطورة: عالية**

في بعض المواضع:

- `amount` يعني صافي القيمة.
- في مواضع أخرى يعني الإجمالي.
- في التحصيل يعني المبلغ المدفوع.
- في الفاتورة قد يكون قبل الضريبة.
- في الإيداع يعني القيمة البنكية.
- في التقرير يتم اختيار `total` قبل `amount`.

مثال الواجهة:

```ts
payload.total ?? payload.amount ?? payload.lineTotal ?? payload.value
```

بينما بعض مسارات PHP تستخدم:

```php
$payload['amount'] ?? $payload['total'] ?? 0
```

### الأثر

قد يتم:

- عرض رقم مختلف عن الرقم المستخدم في الأستاذ.
- إنشاء قيد بقيمة صافية بدل الإجمالية.
- حساب الذمم على قيمة مختلفة عن قيمة الفاتورة.
- تصدير CSV برقم مختلف عن المركز المالي.

### المطلوب

تثبيت قاموس مالي:

| الحقل | المعنى |
|---|---|
| `subtotal` | القيمة قبل الضريبة |
| `taxAmount` | قيمة الضريبة |
| `total` | الإجمالي بعد الضريبة |
| `amount` | يستخدم فقط للتحصيل/المصروف/المرتجع |
| `currency` | العملة |
| `taxInclusive` | هل القيمة المدخلة شاملة الضريبة |

ولا يتم استخدام `amount` كبديل عام لجميع الحقول.

## H-03 — الفواتير القديمة قد تكون بلا علاقة رسمية

في قاعدة البيانات الاحتياطية تم العثور على فواتير لا تحتوي على:

```text
customerRecordId
```

رغم وجود:

```text
customerName
invoiceNumber
```

أمثلة من البيانات السابقة:

- فاتورة `INV-2026-0003`
- فاتورة `#3`

### الأثر

- المطابقة تعتمد على الاسم أو رقم الفاتورة.
- لا يمكن ضمان أن العميل هو صاحب الفاتورة.
- التقارير لا تستطيع بناء كشف رسمي موثوق.
- تغيير اسم العميل قد يقطع العلاقة.

يوجد تقرير ترقية سابق يوضح:

- عدد السجلات المفحوصة: 6
- السجلات القابلة للترقية: 2
- السجلات غير المحسومة: 3

ومن بينها:

- سندا قبض بلا علاقة رسمية وحيدة.
- حركة دفع بلا عميل رسمي مطابق.

### التوصية

عدم تطبيق الترقية التلقائية على السجلات غير المحسومة. يجب إنشاء شاشة مراجعة يدوية قبل اعتمادها.

# 4. مشاكل التحصيل والأرصدة

## H-04 — مسار السداد العام لا يتحقق من تجاوز رصيد العقد

**درجة الخطورة: عالية**

مسار التسوية المتخصص يتحقق من:

- مجموع التوزيعات.
- رصيد العقد.
- رصيد الفاتورة.
- تطابق العميل.
- تطابق الفاتورة بالعقد.

لكن مسار إنشاء سجل مالي عام:

```text
POST /admin/container-system/records
```

يتحقق بشكل عام من أن القيمة أكبر من صفر، لكنه لا يمنع بالضرورة:

- تحصيلًا يتجاوز المتبقي.
- سدادًا على فاتورة مسددة بالكامل.
- سدادًا على عقد مغلق.
- تكرار التحصيل لنفس الفاتورة.

### الأثر

توجد نافذتان للحفظ:

1. نافذة السداد العامة.
2. نافذة التسويات.

وقد تعطي كل نافذة نتيجة مالية مختلفة لنفس العقد.

### المطلوب

توحيد المسارين بحيث يستدعي السداد العام نفس خدمة التسوية المركزية، أو منع حفظ `payment` العام إلا من خلال منطق التوزيع.

## H-05 — حساب الرصيد يعتمد أحيانًا على رقم العقد بدل المعرّف

في عدة مواضع يتم العثور على العقد عن طريق:

```ts
contractNumber
```

بدل:

```ts
contractRecordId
```

ويتم كذلك ربط السداد بالفاتورة عن طريق:

```ts
invoiceNumber
```

### الأثر

- أرقام قديمة أو مكررة تسبب ربطًا خاطئًا.
- تعديل رقم العقد قد يفصل التحصيل عن العقد.
- وجود أكثر من سجل بنفس الرقم في قاعدة قديمة قد يغير نتيجة المطابقة.
- العلاقة المحاسبية النهائية تصبح معتمدة على نص قابل للتعديل.

### المطلوب

المعرّفات الرسمية هي المصدر الأساسي:

```text
customerRecordId
contractRecordId
invoiceRecordId
paymentRecordId
```

أما الأرقام والأسماء فتستخدم فقط للعرض والطباعة والبحث.

## H-06 — توزيع السداد يحفظ `invoiceId` اختياريًا دون إلزام عند وجود فاتورة

النظام يسمح بتوزيع على عقد بدون تحديد فاتورة، حتى لو كانت هناك فواتير مرتبطة بالعقد.

هذا قد يكون صحيحًا تجاريًا إذا كان السداد دفعة مقدمة أو دفعة عامة، لكنه يحتاج إلى تعريف واضح:

- هل السداد على العقد؟
- أم على فاتورة؟
- أم دفعة مقدمة؟
- كيف يوزع لاحقًا على الفواتير؟
- هل يظهر كرصيد دائن للعميل؟

حاليًا لا توجد بنية واضحة للدفعة المقدمة أو الرصيد الدائن.

# 5. مشاكل المرتجعات

## H-07 — تحقق `payment_return` في Node مشروط بوجود رقم فاتورة

في Node، منطق التحقق من `payment_return` موجود داخل كتلة يتم تنفيذها عند وجود:

```ts
invoiceNumber
```

وبالتالي يمكن أن تصل حركة مرتجع سداد تحتوي على:

```text
originalPaymentId
```

لكن دون:

```text
invoiceNumber
```

ولا تمر بكل التحقق المتوقع من السداد الأصلي.

### المطلوب

يجب فصل التحقق إلى مسار مستقل:

```ts
if (kind === "payment_return") {
  validateOriginalPayment(...)
}
```

دون ربطه بوجود رقم فاتورة.

نسخة PHP تبدو أكثر تشددًا في هذه النقطة، وهذا يعني أن هناك عدم تطابق بين Node وPHP.

الواجهة وAPI يستبعدان المؤرشف فقط عند حساب المرتجعات.

بالتالي يمكن أن يؤثر مرتجع:

على:

## H-09 — اتجاه القيود لبعض المرتجعات يحتاج تصحيحًا محاسبيًا

في إنشاء قيد الأستاذ يتم استخدام اتجاهات عامة:

- المصروفات والمرتجعات: `debit`
- الفواتير: `debit`
- التحصيل: `credit`

لكن `invoice_return` و`payment_return` ليسا نفس النوع محاسبيًا.

عادةً:

- مرتجع الفاتورة يؤثر على الإيراد/الذمم بعكس الفاتورة.
- مرتجع السداد يؤثر على النقدية/البنك بعكس التحصيل.

لا يمكن اعتماد الاتجاه الحالي قبل اعتماد دليل حسابات واضح.

# 6. مشاكل منع التكرار

## H-10 — حماية idempotency غير ذرية

يوجد بحث عن مفتاح العملية قبل تنفيذ المعاملة:

```ts
findByOperationKey(...)
```

ثم بعد ذلك يتم إنشاء السداد.

لكن لا يوجد قيد فريد على:

```text
kind + operationKey
```

داخل قاعدة البيانات.

### سيناريو الخطر

إذا وصل طلبان في نفس اللحظة:

1. الطلب الأول يبحث ولا يجد المفتاح.
2. الطلب الثاني يبحث ولا يجد المفتاح.
3. كلاهما يبدأ الإنشاء.
4. يتم إنشاء دفعتين بنفس المفتاح.

### المطلوب

إضافة حماية قاعدة بيانات حقيقية، مثل:

- عمود `operation_key`.
- فهرس فريد جزئي للحركات غير المؤرشفة.
- أو جدول منفصل لمفاتيح العمليات.

ويجب أن تكون إعادة المحاولة بنفس المفتاح:

- تعيد نفس السداد.
- تعيد نفس القيد.
- وترفض أي حمولة مختلفة.

الحماية الحالية جيدة وظيفيًا في الحالة العادية، لكنها ليست كافية ضد التزامن.

---

# 7. مشاكل الإيداعات والمطابقة البنكية

## H-11 — الإيداع لا يفرض دائمًا علاقة صحيحة بالعميل أو التحصيل

في مسار التسوية، يتم التحقق من:

- وجود الإيداع.
- عدم ربطه بسداد سابق.
- تطابق مبلغ الإيداع مع مبلغ السداد.

لكن لا يتم ضمان كل العلاقات التالية بشكل كامل:

```text
الإيداع ← نفس العميل
الإيداع ← نفس الحساب البنكي/الخزينة
الإيداع ← نفس مجموعة التوزيعات
```

كما أن الإيداع قد يحتوي على علاقة واحدة فقط مع العقد الأول.

---

## H-12 — المطابقة الحالية تقارن الإجماليات فقط

المطابقة في واجهة:

```ts
difference = deposits - receipts
```

هذه مقارنة إجمالية وليست مطابقة مستندية.

لا يتم إثبات:

- أي سند قبض دخل في الإيداع.
- أي دفعة تخص أي إيداع.
- وجود فرق بسبب رسوم البنك.
- وجود إيداع جزئي.
- وجود إيداع مجمع لعدة تحصيلات.
- سبب الفرق ومن اعتمده.

### المطلوب

إنشاء نموذج مطابقة يحتوي:

```text
المبلغ المتوقع
المبلغ الفعلي
الفرق
سبب الفرق
المعتمد
الحالة
المستندات المرتبطة
```

---

# 8. مشاكل المصروفات والربحية

## H-13 — احتمال مضاعفة تكلفة الصيانة

في ملف:

```text
ContainerRecordProfile.tsx
```

يتم حساب التكاليف بجمع:

- المصروفات من نوع `expense`.
- تكاليف `maintenance`.

إذا كان نفس الحدث محفوظًا مرة كمصروف ومرة كصيانة، فسيتم احتسابه مرتين.

مثال محتمل من البيانات السابقة:

- مصروف صيانة: 1450 ريال.
- سجل صيانة: 1450 ريال.

### الأثر

- تضخيم التكاليف.
- خفض الربحية بشكل وهمي.
- نتائج مختلفة بين ملف الحاوية والمركز المالي.

### المطلوب

تحديد هل:

- `maintenance` سجل تشغيلي فقط دون أثر مالي.
- أم هو مصروف مالي.
- أم يجب ربطه بمصروف واحد وعدم جمع الاثنين.

---

## H-14 — صافي التدفق لا يشمل كل الحركات المالية

في المركز المالي، المصروفات تشمل:

- `expense`
- `daily_expense`
- `fuel_expense`
- `salary_payment`
- `salary_advance`

لكن لا يظهر بوضوح إدراج:

- العمولات.
- المشتريات.
- مرتجعات المشتريات.
- التحويلات.
- الإيرادات الأخرى.
- تأثير المخزون.
- رسوم البنوك.

لذلك فإن:

```text
netCash
```

ليس بالضرورة صافي التدفق النقدي الحقيقي.

---

## H-15 — العمولات يمكن أن تكون بلا مبلغ

في البيانات السابقة يوجد سجل عمولة يحتوي على:

```text
rate
basis
```

لكن لا يحتوي على:

```text
amount
```

ومع ذلك يظهر ضمن الحركات المالية.

### الأثر

- تظهر الحركة بقيمة صفر.
- قد تُعد حركة مالية معتمدة دون قيمة.
- التقارير تعرض عدد العمولة دون أثر مالي حقيقي.

### المطلوب

إما:

- حساب مبلغ العمولة عند الإنشاء.
- أو اعتبار السجل إعدادًا وليس حركة مالية.
- أو منع ترحيل العمولة قبل تحديد القيمة.

---

# 9. مشاكل التقارير والواجهة

## H-16 — الواجهة تعرض القيم بالتقريب إلى أقرب ريال

عدة أجزاء تستخدم:

```ts
Math.round(value).toLocaleString("ar-SA")
```

وهذا يخفي الكسور، مثل:

```text
100.50
```

فتظهر:

```text
101
```

### الأثر

- فرق بين التقرير والدفتر.
- صعوبة مطابقة الضريبة والعمولات.
- فقدان دقة القيم في العرض والطباعة.

### المطلوب

استخدام منزلتين عشريتين في كل القيم المالية:

```ts
Intl.NumberFormat("ar-SA", {
  minimumFractionDigits: 2,
  maximumFractionDigits: 2,
})
```

---

## H-17 — التقرير العام يستخدم منطقًا عامًا للحقول المالية

رغم وجود تحسن في استبدال التخمين، ما زالت بعض التقارير تستخدم منطقًا عامًا مثل:

```ts
total ?? amount ?? lineTotal ?? value
```

وهذا غير مناسب لكل نوع حركة.

مثال:

- في الفاتورة يجب استخدام `total`.
- في التحصيل يجب استخدام `amount`.
- في المصروف يجب استخدام `amount`.
- في بند الفاتورة يجب استخدام `lineTotal`.
- في المرتجع يجب استخدام `amount`.

### المطلوب

تعريف مصدر صريح لكل تقرير ولكل نوع حركة، وعدم استخدام دالة واحدة لجميع الأنواع.

---

## H-18 — بعض الفلاتر تعرض كأنها فعالة لكنها ليست كذلك

في التقارير، بعض الفلاتر التي لا توجد لها خريطة حقول تظهر كشارات نصية فقط، ولا تعمل كفلتر فعلي.

هذا لا يغير المبلغ مباشرة، لكنه قد يجعل المستخدم يظن أنه يرى تقريرًا مفلترًا بينما البيانات لم تتغير.

---

# 10. مشاكل قاعدة البيانات والتصميم المالي

## H-19 — القيم المالية موجودة داخل JSON فقط

الجدول الأساسي هو:

```text
container_system_records
```

والقيمة والعلاقات داخل:

```text
payload
```

### مخاطر ذلك

- لا توجد قيود SQL على المبلغ.
- لا يوجد فهرس فريد على أرقام الفواتير.
- لا توجد علاقات Foreign Key بين العميل والعقد والفاتورة والسداد.
- لا يوجد تحقق ذري من عدم تجاوز الرصيد.
- صعوبة تنفيذ تقارير دقيقة.
- بطء البحث مع نمو البيانات.
- صعوبة منع التكرار في التزامن.

### القرار المقبول مؤقتًا

يمكن إبقاء `payload` في المرحلة الحالية لتجنب هجرة كبيرة، لكن يجب إضافة طبقة قيود مالية، على الأقل:

- جدول توزيعات.
- أعمدة مرجعية واضحة.
- فهارس.
- مفتاح عملية مستقل.
- قيود مبالغ.
- سجل عكوس للحركات.

---

## H-20 — لا يوجد حقل عملة واضح

النظام يعرض:

```text
ر.س
```

بشكل ثابت في الواجهة.

لكن السجل المالي نفسه لا يفرض:

```text
currency
```

### الأثر

- لا يمكن دعم عملة أخرى.
- لا يمكن التأكد من أن الإيداع والفاتورة بنفس العملة.
- لا يمكن إجراء تحويل أو تقرير متعدد العملات بشكل صحيح.

حتى لو كان النشاط حاليًا بالريال السعودي، يجب حفظ:

```text
currency: SAR
```

في كل مستند مالي أو على مستوى المؤسسة.

---

## H-21 — استخدام JavaScript Number للحسابات المالية

الحسابات تعتمد على `Number`، مثل:

```ts
sum + Number(amount)
```

وهذا قد يسبب فروقات ثنائية صغيرة مع الكسور.

يوجد تسامح:

```ts
0.01
```

لكن ذلك لا يعالج كل الحالات.

### المطلوب

استخدام أحد الخيارين:

1. تخزين المبالغ كهللات صحيحة:
   ```text
   amountMinor = 105050
   ```
2. استخدام Decimal مخصص للحسابات المالية.

# 11. التوافق بين Node وPHP/Hostinger

## H-22 — اختلاف في قيمة القيد عند إنشاء سجل مالي عام

في Node عند إنشاء القيد يتم استخدام:

```ts
payload.amount ?? payload.total ?? 0
```

بينما في PHP في مسار الإنشاء العام يتم استخدام:

```php
$payload['amount'] ?? 0
```

فإذا كان المستند يحتوي على `total` فقط دون `amount`، قد ينشأ قيد PHP بقيمة صفر رغم أن المستند المالي له قيمة.

### المطلوب

توحيد المعادلة في Node وPHP، ويفضل عدم استخدام fallback عام، بل تحديد القيمة حسب نوع المستند.

---

## H-23 — ترميز JSON في PHP غير موحد

بعض مواضع PHP تستخدم:

```php
JSON_UNESCAPED_UNICODE
```

بينما مواضع أخرى تستخدم:

```php
JSON_INVALID_UTF8_SUBSTITUTE
```

### الأثر

إذا احتوى نص قديم على ترميز غير صالح، قد يفشل حفظ أو إخراج JSON، أو تظهر استجابة فارغة.

يجب توحيد الترميز في كل:

- INSERT.
- UPDATE.
- الاستجابة.
- سجل التدقيق.
- إنشاء القيد.

---

## H-24 — التوافق بين Node وPHP جيد جزئيًا فقط

تمت مطابقة جوانب مهمة مثل:

- إنشاء قيد الأستاذ.
- منع إعادة ربط الإيداع.
- التحقق من مفتاح العملية.
- دورة الاعتماد.

لكن ما زالت توجد اختلافات في:

- معالجة `taxInclusive`.
- التحقق من `payment_return`.
- علاقة الإيداع بالتوزيعات.
- اختيار قيمة القيد.
- حالات الحركات التي تدخل في التقارير.
- بعض العلاقات الرسمية بين العميل والعقد والفاتورة.

لذلك لا يمكن اعتبار نسخة Hostinger مطابقة بالكامل للنسخة المحلية.

# 12. نتائج فحص البيانات

## قاعدة البيانات النشطة

قاعدة البيانات النشطة الحالية تحتوي على سجلات تشغيلية للحاويات، ولا تحتوي في النسخة المفحوصة على مجموعة مالية كاملة قابلة للمطابقة.

هذا يعني أن:

- عدم ظهور أرقام مالية في النسخة الحالية لا يثبت سلامة النظام.
- لا توجد حاليًا بيانات مالية نشطة كافية لإثبات تطابق المركز المالي.
- يجب اختبار الدورة على بيانات مالية حقيقية أو مجموعة اختبار مكتملة.

## النسخ المالية السابقة

تم العثور على الحالات التالية:

- سندات قبض بلا علاقة رسمية واضحة.
- حركة دفع بلا عميل رسمي مطابق.
- فواتير بلا `customerRecordId`.
- قيود أستاذ قديمة بلا `sourceId`.
- عمولة بلا مبلغ.
- سجلات قديمة تعتمد على أسماء العملاء والأرقام فقط.
- احتمال وجود ازدواجية بين `receipt` و`payment`.

## مشكلة أداة التدقيق

أداة:

```text
scripts/audit-db-architecture.mjs
```

فشلت أثناء التنفيذ بسبب استعلام يعتمد على عمود `name` غير الموجود في أحد الجداول.

هذه ليست مشكلة مالية مباشرة، لكنها تعني أن أدوات التحقق نفسها ليست جاهزة للاعتماد عليها كفحص نهائي دون إصلاح.

# 13. الأولويات المطلوبة

## الأولوية الأولى — يجب إصلاحها قبل الاعتماد المالي

1. احتساب `posted` فقط في جميع الأرقام.
2. منع احتساب `receipt` و`payment` لنفس العملية مرتين.
3. معالجة إلغاء الحركات المرحّلة بقيد عكسي.
4. توحيد علاقة الإيداع مع كل توزيعات السداد.
5. منع السداد الذي يتجاوز الرصيد في كل المسارات.
6. إصلاح تحقق `payment_return`.
7. إضافة حماية ذرية لمفتاح idempotency.
8. توحيد Node وPHP في حساب الضريبة والقيد.

## الأولوية الثانية

1. توحيد `amount`, `subtotal`, `taxAmount`, `total`.
2. إضافة علاقات رسمية ثابتة للعميل والعقد والفاتورة والسداد.
3. منع اعتماد الفاتورة دون عميل رسمي.
4. إنشاء شاشة مراجعة للسجلات القديمة غير المرتبطة.
5. منع مضاعفة المصروفات والصيانة.
6. مراجعة اتجاهات القيود المحاسبية.
7. إضافة `currency`.
8. استخدام منزلتين عشريتين في العرض والتقارير.

## الأولوية الثالثة

1. تقرير أعمار الذمم.
2. تقرير التدفق النقدي الحقيقي.
3. تقرير مطابقة الإيداعات بالتفصيل.
4. تقرير القيود العكسية.
5. تقرير السجلات غير المرتبطة.
6. تصدير CSV/PDF بمصدر كل رقم.
7. إقفال يومي وشهري للفترات المالية.
8. اعتماد ثنائي للمرتجعات والمبالغ الكبيرة.

# 14. الحكم النهائي

النظام في وضعه الحالي **مناسب كدورة مالية تشغيلية داخلية تحت المراجعة**، لكنه غير جاهز بعد ليكون مصدرًا محاسبيًا نهائيًا أو مرجعًا وحيدًا للأرقام بسبب:

- تضارب محتمل بين أنواع التحصيل.
- احتساب حالات غير مرحّلة.
- ضعف العلاقة بين الإيداع والتوزيعات.
- عدم اكتمال معالجة الإلغاء والمرتجعات.
- اختلافات Node وPHP.
- اعتماد كبير على JSON والأرقام النصية.
- عدم ثبات معنى الحقول المالية.

## النتيجة النهائية

**مستوى الجاهزية الحالي: متوسط مع مخاطر مالية مرتفعة.**

لا أوصي باعتماد:

- إجمالي التحصيل.
- المتبقي.
- صافي التدفق.
- المطابقة البنكية.
- الربحية.
- أرصدة العملاء.

كأرقام نهائية قبل تنفيذ إصلاحات الأولوية الأولى وإعادة اختبار دورة كاملة تشمل:

```text
عميل
→ عقد
→ فاتورة
→ سداد
→ توزيع
→ إيداع
→ مرتجع
→ إلغاء/تصحيح
→ قيد أستاذ
→ تقرير
```

تمت أيضًا إتاحة ثلاثة أعمال متابعة عالية الأولوية لمعالجة هذه الفجوات: استبعاد الحركات غير المرحّلة، ضمان عدم تكرار التحصيل ومطابقة الإيداعات، وتوحيد الضريبة والقيم العشرية.
