كمل التنفيذ من الحالة الحالية، لكن انتبه جيدًا: **مشروعي لا يدعم Node في الإنتاج ولا أريد أي حل يعتمد على Node/Express. الإنتاج هو Hostinger + PHP + SQLite، وأي Node موجود في المستودع هو للتطوير/البناء فقط ما لم يثبت العكس.**

هناك الآن مشكلتان حقيقيتان يجب إغلاقهما بالكامل، ولا أريد خطة أو تدقيقًا جديدًا. **نفّذ مباشرة ثم اختبر.**

# أولًا: مشكلة Flash / Loading في جميع الصفحات

حاليًا عند فتح:

* لوحة التقارير والتحليلات
* صفحة تسجيل الدخول
* والصفحات الأخرى عمومًا

تظهر بيانات/عناصر أولية أثناء التحميل ثم تختفي، وبعد اكتمال التحميل يظهر المحتوى الحقيقي.

هذا السلوك **مرفوض بصريًا**.

لا أريد مجرد زيادة `setTimeout` أو إخفاء المشكلة بـspinner عشوائي.

أريد تحديد السبب المعماري الحقيقي، وغالبًا سيكون واحدًا أو أكثر من:

* hydration mismatch
* initial state خاطئ
* تحميل settings بعد أول render
* auth state غير محسوم
* API data تبدأ بقيمة افتراضية ثم تستبدل
* route/page rendering قبل اكتمال bootstrap
* skeleton غير موحد
* مكونات تعرض بيانات fallback ثم تستبدلها بالبيانات الحقيقية
* React effect يعيد تركيب المحتوى بعد mount
* layout أو context يعيد render الصفحة مرتين
* SSR/prerender/static HTML لا يطابق أول React render

## المطلوب

افحص المشكلة على مستوى **النظام كله** وليس صفحة واحدة.

ابحث عن جميع الأنماط التي تسبب:

* content flash
* stale initial content
* placeholder content ثم replacement
* flash of authenticated/unauthenticated state
* flash of default settings
* flash of empty/default analytics
* layout shift بسبب انتظار البيانات

ثم أصلح السبب المشترك قدر الإمكان.

### شرط مهم

لا تجعل المستخدم يرى:
`بيانات قديمة → تختفي → بيانات حقيقية`

ولا:
`محتوى افتراضي → يختفي → محتوى API`

ولا:
`صفحة كاملة → تختفي → صفحة أخرى`

بل يجب أن يكون هناك **loading state مقصود ومتناسق** إلى أن تتوفر البيانات اللازمة.

إذا كانت البيانات لا يمكن عرضها قبل API، اعرض Skeleton مناسبًا للمكان بدل عرض بيانات وهمية.

أما البيانات التي يمكن معرفتها من الـURL أو static build فلا تنتظر API بلا داعٍ.

## اختبر ذلك على الأقل في:

* Login
* Home
* Dashboard
* Analytics
* Reports
* أي صفحات تعتمد على SiteSettings
* أي صفحات تعتمد على Authentication
* الصفحات التي تعتمد على API data
* صفحات الإدارة
* صفحات العملاء/الخدمات إن وجدت

استخدم browser/runtime inspection وتأكد أن أول حالة مرئية للمستخدم هي الحالة الصحيحة أو Skeleton، وليس محتوى خاطئًا مؤقتًا.

**لا أريد إصلاح صفحة Analytics فقط إذا كان السبب موجودًا في Context/Layout مشترك.**

# مهم جدًا: لا تستخدم Node كحل إنتاجي

مرة أخرى:

**الإنتاج = Hostinger + PHP + SQLite.**

لا تضف:

* Express route جديد كحل للإنتاج
* Node server dependency
* Node runtime requirement
* reverse proxy يتطلب Node
* أي API production architecture تعتمد على Node

إذا احتجت تعديل API للإنتاج، عدّل:

`PHP router / api-index.php`

والملفات التي تدخل فعلًا في أرشيف Hostinger.

Node يمكن استخدامه فقط أثناء build/test المحلي إذا كان جزءًا من toolchain، وليس كمتطلب تشغيل للإنتاج.
