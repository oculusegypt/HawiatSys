
ويجب أن تكون البيانات فريدة ولا تعتمد على بيانات قديمة أو على نجاح اختبارات سابقة.

# 2. اختبار الفصل الحقيقي بين Requests و Work Orders

هذه نقطة أساسية جدًا.

أنشئ سيناريو كامل يحتوي على:

* Customer
* Customer Site
* Container / Asset
* Contract
* Driver / Employee
* Delivery operation
* Pickup / Return operation
* Emptying operation

ثم سجل عدد `service_requests` قبل العمليات.

بعد إنشاء العمليات الثلاث:

```text
Delivery
Pickup / Return
Emptying
```

تحقق بشكل صريح أن:

```text
عدد service_requests لم يزد بسبب العمليات التشغيلية
```

أي أن:

```text
Commercial Customer Request
!=
Operational Work Order
```

ولا أريد نجاحًا شكليًا بمجرد ظهور شيء في الواجهة.

يجب إثبات أن كل عملية موجودة كسجل:

```text
work_order
```

وليس:

```text
service_request
```

# 3. اختبر دورة أمر العمل كاملة لكل نوع عملية

لكل من:

### Delivery

### Pickup / Return

### Emptying

اختبر دورة حقيقية مثل:

```text
Created
→ Assigned
→ Accepted
→ Started
→ En Route
→ Arrived
→ Completed
```

حسب الحالات الفعلية المدعومة في النظام.

ويجب التحقق بعد كل مرحلة من:

* حالة أمر العمل
* السائق المرتبط
* العميل
* العقد
* الحاوية
* الموقع
* الموعد
* سجل التدقيق

ولا تكتفِ بتغيير قيمة status مباشرة في قاعدة البيانات.

الاختبار يجب أن يمر عبر الـAPI / Workflow الحقيقي.

---

# 4. اختبر الإصلاح الأخير الخاص بإكمال الحاوية

هذا هو الـBug الذي اكتشفته بنفسك، وبالتالي يجب أن يكون له اختبار صريح.

عند:

```text
Complete Delivery
```

تحقق من حالة:

* Work Order
* Contract
* Container / Asset
* Assignment إن وجدت
* الموعد

وعند:

```text
Complete Pickup / Return
```

تحقق أن حالة الحاوية والعقد تتغير وفق منطق الاسترجاع الحقيقي.

وعند:

```text
Complete Emptying
```

تحقق أن العملية تؤثر على الحالة التشغيلية المطلوبة فقط، ولا تنشئ طلب عميل جديد ولا تؤثر ماليًا.

**إذا فشل أي انتقال حالة، أصلحه ثم أعد الاختبار كاملًا من البداية.**

---

# 5. منع التكرار Idempotency

لكل عملية:

```text
Delivery
Pickup
Emptying
```

نفذ إعادة الطلب بنفس مفتاح العملية.

يجب إثبات عدم إنشاء:

* Work Order ثانٍ
* Appointment ثانٍ
* Assignment ثانٍ
* Audit event غير منطقي

ثم جرّب طلبًا مختلفًا قد يسبب تكرار نفس العملية، وتحقق من أن قواعد منع التكرار تعمل حسب منطق النظام.

أريد أرقامًا واضحة قبل وبعد، مثل:

```text
Work Orders before: X
Work Orders after first request: X + 1
Work Orders after retry: X + 1
```

---

# 6. اختبر زر «تجهيز العقد» فعليًا في الواجهة

كان عندنا Bug سابق يحول الزر إلى:

```text
view=settlements
```

وهذا غير مقبول.

اختبر الزر من الواجهة الحقيقية.

يجب أن:

* لا يفتح التسويات المالية
* لا يحول المستخدم إلى صفحة مالية
* يفتح مساحة تشغيل العقد الصحيحة أو الـworkflow الصحيح
* يحمل `contractId` الصحيح
* يعرض الحاوية المرتبطة
* يسمح بإنشاء العملية التشغيلية المناسبة

اختبر النتيجة فعليًا، وليس بمجرد مراجعة الرابط في الكود.

---

# 7. راجع جميع أزرار العمليات السريعة

راجع كل الأزرار الموجودة في مساحة العقد، ومنها على الأقل:

* تسليم الحاوية
* استرجاع / سحب الحاوية
* تفريغ الحاوية
* تجهيز العقد
* إغلاق العقد إذا كان موجودًا

لكل زر:

1. ماذا يفعل؟
2. ما السجل الذي ينشئه؟
3. هل ينشئ `service_request` بالخطأ؟
4. هل ينشئ `work_order`؟
5. هل يربط العميل؟
6. هل يربط العقد؟
7. هل يربط الحاوية؟
8. هل ينشئ موعدًا عند الحاجة؟
9. هل يمكن إسناده لسائق؟
10. هل يكتمل الـworkflow؟

أي زر معطل أو يذهب لمسار خاطئ يجب إصلاحه.

# 9. لا تنسَ المشاكل السابقة التي ما زالت حساسة

أثناء تنفيذ هذا الإصلاح، لا تكسر دورة:

```text

→ Contract
→ Invoice
→ Payment
```

نفذ Regression على الأقل للتحقق من:

### Invoice

* العميل مرتبط
* العقد مرتبط
* الحاوية مرتبطة
* لا تظهر `غير مرتبط` إذا كانت العلاقة موجودة
* المدفوع لا يتضاعف
* المتبقي صحيح

### Payment

```text

```


```text

```

ولا يجوز أن يكون جمع السداد محسوبًا مرتين من:

* Payment record
* allocations
* financial transaction
* أو أي مصدرين معًا

حدد **مصدر الحقيقة الواحد** للحساب، ووحّد القراءة في:

* ملف العميل
* ملف العقد
* تفاصيل الفاتورة
* قائمة الفواتير
* تفاصيل السداد
