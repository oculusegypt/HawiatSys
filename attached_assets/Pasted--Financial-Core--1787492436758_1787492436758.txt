# أمر التنفيذ النهائي — إزالة الازدواج المالي واعتماد Financial Core كمصدر وحيد للحقيقة

ما تم تنفيذه حتى الآن **يُعتبر تقدماً تنفيذياً حقيقياً ومقبولاً**.

إنشاء الـ Financial Core، والجداول typed، والـ Chart of Accounts، والقيود المحاسبية، والعكس، والفترات المالية، والمطابقة البنكية، والاختبارات الأساسية؛ كلها خطوات صحيحة.

لكن **لا تعتبر المهمة مكتملة**.

المشكلة المتبقية الآن واضحة ومحددة:

> النظام يحتوي على Financial Core جديد، بينما بعض التقارير والواجهات والمسارات القديمة ما زالت تقرأ مباشرة من `container_system_records`.

وهذا يعني أن لدينا حالياً **مصدرين محتملين للحقيقة المالية**.

وهذا غير مقبول في النسخة النهائية.

---

# القرار

من الآن:

> **Financial Core هو المصدر الوحيد للحقيقة المالية داخل النظام.**

يجب ألا يبقى أي تقرير أو Dashboard أو API أو Service أو Component مالي يعتمد مباشرة على `container_system_records` للحصول على قيمة مالية نهائية.

`container_system_records` يمكن أن يبقى فقط كمصدر تاريخي/Legacy أو كطبقة توافق مؤقتة عند الحاجة، ولكن **ليس كمصدر للحسابات المالية النهائية**.

# 1. Audit كامل لكل المستهلكين الماليين

ابحث بشكل شامل في المشروع عن كل استخدام لـ:

* `container_system_records`
* أي Queries مالية قديمة.
* أي حسابات مالية داخل Routes.
* أي حسابات مالية داخل Services.
* أي حسابات مالية داخل Components.
* أي Aggregations مستقلة.
* أي Dashboard يحسب الإيرادات أو المصروفات بنفسه.
* أي تقرير يبني الرصيد من JSON أو Records مباشرة.

لا تفترض أن الملفات المذكورة هي كل الملفات.

اعمل Search شامل للـ repository.

لكل استخدام، صنفه إلى:

### A — Financial Source

يجب نقله إلى Financial Core.

### B — Historical / Operational Data

يمكن الإبقاء عليه إذا لم يكن مصدراً للحقيقة المالية.

### C — Compatibility Layer

يمكن إبقاؤه مؤقتاً فقط إذا كان ضرورياً للتوافق، مع منع استخدامه كمصدر مالي.

# 6. منع الحساب المالي المكرر

أي منطق مثل:

```text
payments + receipts
```

أو:

```text
revenue = invoices - refunds
```

أو:

```text
cash = payments - expenses
```

يجب ألا يتكرر في عدة أماكن.

ضع الحساب في طبقة مالية مركزية.

ثم:

```text
API
 ↓
Financial Service
 ↓
Financial Core
 ↓
Journal / Ledger
```

والواجهة تعرض النتيجة فقط.

---

# 7. حل مشكلة Double Counting نهائياً

أنشئ اختبارات تمنع التكرار على مستوى النظام كله.

اختبر الحالات التالية:

### Payment + Receipt

يجب ألا يتم احتسابهما كدخلين مستقلين إذا كان أحدهما تمثيلاً للآخر.

### Invoice + Payment

يجب ألا يتم اعتبار الفاتورة نفسها Cash Revenue.

### Deposit + Payment

يجب ألا يتم احتساب الإيداع مرة أخرى كتحصيل جديد.

### Refund + Original Transaction

يجب أن يظهر الأثر الصافي الصحيح.

### Reversal + Original Entry

يجب ألا يتم احتساب العكس كحركة مستقلة غير مرتبطة.

### Transfer

يجب ألا يؤدي تحويل الأموال بين حسابين إلى زيادة إجمالي النقدية.

# 10. Financial Periods

الـ Financial Periods التي تم تنفيذها يجب أن تصبح جزءاً فعلياً من جميع عمليات الترحيل.

اختبر:

* Invoice داخل فترة مغلقة.
* Payment داخل فترة مغلقة.
* Expense داخل فترة مغلقة.
* Purchase داخل فترة مغلقة.
* Refund داخل فترة مغلقة.
* Reversal داخل فترة مغلقة.
* Adjustment داخل فترة مغلقة.

ولا يكفي منع الترحيل فقط.

يجب منع أي تعديل مالي غير مصرح به على حركة موجودة في فترة مغلقة.

# 11. Legacy Layer

لا تحذف `container_system_records` بشكل أعمى.

أولاً:

1. حدد جميع مستخدميه.
2. حدد البيانات التي لا تزال تعتمد عليه.
3. حدد ما يجب ترحيله.
4. حدد ما هو Historical.
5. حدد ما هو Operational فقط.
6. انقل كل Financial Truth إلى Financial Core.
7. أضف Compatibility Layer عند الحاجة.
8. امنع أي Financial Write جديد إليه إذا أصبح غير مطلوب.

الهدف النهائي:

> `container_system_records` لا يكون Financial Source of Truth.

لن أعتبر Financial Core مكتملًا بمجرد أن:

```text

```

بل يجب أن يتحقق الآتي:

* Financial Core هو المصدر الوحيد للحقيقة.
* لا توجد تقارير مالية تعتمد على `container_system_records`.
* لا توجد حسابات مالية مكررة في الـ APIs.
* لا توجد حسابات مالية مكررة في Frontend.
* لا يوجد Double Counting.
* كل حركة مالية لها Journal Entry.
* كل Journal Entry متوازن.
* كل Allocation صحيح.
* كل Reversal صحيح.
* كل فترة مغلقة محمية.
* Bank Reconciliation تفصيلية.
* Customer/Contract/Invoice balances موحدة.
* Inventory financial impact موحد.
* Profitability مبنية على Ledger.
* PHP متطابقة مع Node.
* Hostinger متطابق مع النظام.
* جميع التقارير تعتمد على نفس Financial Truth.
* End-to-End financial tests ناجحة.
* Cross-report consistency tests ناجحة.
* Production-like dataset ناجح.
* Typecheck ناجح.
* Build ناجح.
* Operational validation ناجح.
* لا توجد أخطاء مالية في logs.

# 20. معيار الاعتماد النهائي

بعد إنهاء التنفيذ، قم بعمل Audit أخير مستقل.

لا تقل:

> "يبدو أن كل شيء يعمل."

بل أثبت:

```text
Financial Core
        ↓
100% Financial Sources
        ↓
100% Journal Coverage
        ↓
100% Report Coverage
        ↓
100% API Coverage
        ↓
100% UI Coverage
        ↓
100% PHP Coverage
        ↓
100% Hostinger Compatibility
        ↓
100% Reconciliation
        ↓
100% End-to-End Tests
```

إذا بقي مسار واحد يقرأ الحقيقة المالية من النظام القديم، **فلا تعلن 10/10**.

إذا تم تحويل كل المسارات فعلياً إلى Financial Core، وجميع الاختبارات والمطابقات نجحت، عندها فقط يمكن إعلان:

> **10/10 — Unified Financial Core — Fully Integrated — Auditable — Reconciled — Production Ready**

---

## الأمر النهائي

**لا تطور Financial Core إضافياً لمجرد التطوير.**

الـ Core الأساسي موجود الآن.

المهمة الحالية هي:

> **ربط كل ما حوله به، إزالة ازدواجية مصادر الحقيقة، اختبار كل المسارات، ثم إثبات أن النظام كله يعمل كنظام مالي واحد.**

لا تغيّر الخطة لتناسب ما تم إنجازه.

**غيّر النظام حتى يحقق النتيجة النهائية.**

وعند الانتهاء، أريد تقريراً مختصراً يوضح لكل فجوة كانت موجودة:

```text
Gap
→ Implementation
→ Files Changed
→ Test
→ Result
→ Evidence
```

ثم الحكم النهائي فقط:

> **10/10 أو لا.**
