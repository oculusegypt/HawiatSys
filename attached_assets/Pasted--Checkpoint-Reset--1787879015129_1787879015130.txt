أكمل من آخر Checkpoint بالضبط، ولا تبدأ من جديد ولا تعمل Reset ولا تحذف أي تعديل سابق.

أريد منك تنفيذ مرحلة الإغلاق النهائية باحتراف، مع اعتبار كل ما يلي متطلبات إلزامية:

### 1. أهم قاعدة: الرابط العام يجب أن يكون ديناميكيًا بالكامل

لا أريد تثبيت `taqigroup.com` أو `alsahmm.com` داخل مكونات الموقع أو SEO أو canonical أو OG أو sitemap أو robots.

يجب أن يكون هناك **مصدر مركزي واحد للحقيقة** للرابط العام، ويُستخرج تلقائيًا من إعداد الموقع/البيئة/الدومين الحالي حسب البنية الموجودة أصلًا.

طبّق ذلك على:

* canonical
* `og:url`
* `og:image`
* JSON-LD
* `Organization`
* `LocalBusiness`
* `WebSite`
* sitemap
* robots.txt
* prerender
* PHP
* أي absolute URL آخر

المهم:

* لا تستخدم `window.location.origin` بطريقة تجعل preview/staging يظهر داخل SEO.
* لا تستخدم دومينًا hardcoded داخل React.
* لا تجعل build خاصًا بدومين واحد.
* يجب أن يعمل الحل إذا تغير الدومين مستقبلًا دون تعديل عشرات الملفات.
* إذا كان `site_public_url` هو مصدر الحقيقة الحالي، استخدمه مركزيًا مع fallback منطقي فقط عند التطوير، وليس كـ hardcoded production domain.

ولا تعدّل قيمة قاعدة البيانات إلى دومين جديد لمجرد التخمين. أولًا أثبت ما هو الـpublic URL المقصود من إعدادات المشروع الحالية.

### 2. favicon / أيقونة نتيجة Google

هذه نقطة مهمة جدًا ولم تُغلق بعد.

أنا أرى أن الموقع لديه favicon، ومع ذلك أداة التقييم تقول إن favicon موجود، لكن **أيقونة الموقع لا تظهر كما ينبغي في نتائج Google**.

لا تخلط بين:

* favicon التي تظهر بجانب نتيجة Google.
* `og:image` التي تستخدم للمشاركة/بعض المعاينات الاجتماعية.
* صورة الـHero.
* Logo داخل JSON-LD.

افحص الثلاثة بشكل مستقل.

أريد منك التأكد من أن favicon:

* ملف حقيقي وصالح.
* مربع.
* أبعاده صحيحة.
* MIME type صحيح.
* HTML يعلن عنه بالـtype الصحيح.
* لا يوجد إعلان خاطئ مثل WebP معلن على أنه PNG.
* manifest لا يحتوي sizes/types غير حقيقية.
* `apple-touch-icon` صحيح إن كان موجودًا.
* `favicon.ico` صالح فعلًا وليس مجرد PNG تمت تسميته ICO.
* توجد نسخة PNG مناسبة يمكن لمحركات البحث والمتصفحات استخدامها.
* الملفات موجودة فعليًا داخل `dist` وداخل Hostinger archive النهائي.
* الروابط لا تعطي 404.
* لا توجد روابط قديمة إلى favicon.webp غير موجود أو غير مناسب.

لكن لا تعدّل هوية الشعار ولا تصمم أي أيقونة جديدة. أي PNG/ICO يتم إنشاؤه يجب أن يكون مشتقًا من الهوية الحالية نفسها.

وأضف إلى SEO gate تحققًا يمنع:

* MIME mismatch
* missing favicon
* non-square favicon
* missing referenced icon
* manifest icon with incorrect dimensions/type

### 3. لا تفترض أن عدم ظهور favicon في Google يعني أن الكود فاشل

بعد التأكد تقنيًا من صحة favicon، وثّق بوضوح أن ظهورها في Google يعتمد أيضًا على إعادة الزحف والتحديث من Google.

المطلوب منك إثبات:
`HTML → favicon URL → HTTP response → MIME → dimensions → archive`

ولا تدّعي أن Google ستعرضها فورًا لمجرد أن HTML صحيح.

### 4. الأداء: ركّز على Mobile أولًا

نتيجة Hostinger الأخيرة على Desktop أصبحت ممتازة نسبيًا:

* Performance = 91
* FCP = 0.8s
* LCP = 1.3s
* Speed Index = 2.3s
* CLS = 0.059
* TBT = 0ms

لكن Mobile ما زال هو المشكلة الكبرى:

* Performance = 37
* FCP = 4.2s
* LCP = 6.6s
* Speed Index = 11.2s
* TBT = 1020ms
* CLS = 0.022

والتقرير الآخر أيضًا أظهر Mobile LCP حوالي 6s مقابل Desktop حوالي 1.5s.

إذن لا تعتبر المهمة منتهية لأن Desktop = 91.

ركّز على الأسباب الجذرية الموجودة فعلًا:

* LCP image discovery
* JavaScript execution
* unused JavaScript
* render-blocking
* enormous network payload
* image delivery
* cache lifetime
* network dependency chain
* redirects
* main-thread work
* forced reflow

ولا تعمل تحسينات عشوائية أو تغييرات تصميمية.

### 5. Hero/LCP

راجع آخر تعديل الذي جعل صورة الـHero الأولى تُستخرج من قاعدة البيانات.

أثبت أن:

* الصورة الأولى الفعلية هي نفسها التي يتم preload لها.
* preload موجود في HTML قبل تشغيل JavaScript.
* `fetchpriority="high"`/الأولوية المناسبة مستخدمة فقط للـLCP الحقيقي.
* الصورة الأولى ليست lazy.
* الصور الأخرى لا يتم تحميلها كلها مبكرًا.
* لا يتم تحميل صور السلايدر غير الضرورية عند أول دخول.
* لا يحدث تحميل مزدوج لنفس Hero من الـstatic HTML ثم React.
* الصورة موجودة فعليًا داخل archive.
* لا يوجد redirect للصورة.
* الحجم والصيغة مناسبان.

الأهم: لا تعتمد على تخمين اسم الصورة. استخرجها من مصدر البيانات الفعلي الموجود في المشروع.

### 6. الصور أسفل الصفحة

راجع التعديلات الأخيرة على:

* ServiceCard
* BlogSection
* AboutSection
* CEOMessage
* Partners

وتأكد أن:

* الصور أسفل الـfold lazy.
* لها width/height أو aspect-ratio ثابت.
* لا يوجد CLS.
* لا يتم lazy-load لصورة هي LCP.
* لا يوجد تحميل مكرر.
* لا توجد صور كبيرة جدًا بلا داعٍ.

### 7. SEO

بعد انتهاء التعديلات، يجب أن تفحص HTML الناتج نفسه، وليس React source فقط.

للصفحة الرئيسية وصفحات ممثلة من:

* service
* neighborhood
* article

تحقق من:

* `<title>`
* meta description
* canonical
* og:url
* og:title
* og:description
* og:image
* og:image:type
* Twitter metadata إن كانت موجودة
* JSON-LD
* H1
* robots
* internal links
* الصور المحلية

ويجب ألا يوجد:

* preview domain
* domain قديم
* duplicate canonical
* duplicate OG tags
* localhost
* Replit/preview URL
* missing H1 في الصفحة الرئيسية
* JSON-LD يشير لدومين مختلف عن canonical

### 8. Sitemap وrobots

يجب أن يكونا مولدين من نفس مصدر الـpublic URL المركزي.

لا تستخدم:
`Host`
الوارد من request كمصدر وحيد للـproduction canonical/sitemap إذا كان ذلك يسمح بتسريب preview/staging.

وفي الوقت نفسه لا hardcode production domain.

تحقق من:

* sitemap URLs
* sitemap image URLs
* robots Sitemap URL
* عدم وجود preview URLs
* عدم وجود localhost
* عدم وجود duplicate URLs
* تطابق sitemap مع الصفحات التي تم prerender لها.

### 9. PHP وNode يجب أن يظلا متطابقين

أي إصلاح SEO أو URL أو analytics يجب أن يكون متوافقًا في:

* Node
* PHP
* SQLite
* prerender
* Hostinger

خصوصًا مشكلة `utm_source` السابقة:
لا تكتفِ بأن الاستعلام يعمل على قاعدة محلية واحدة.

اختبر:

* schema الحالي
* schema الجديد
* قاعدة SQLite المستخدمة في Hostinger archive
* PHP analytics
* Node analytics

وتأكد من عدم وجود column mismatch بين Drizzle وPHP.

### 10. لا تخلط مشاكل الاختبارات القديمة بالمهمة

إذا ظهر failure غير متعلق بهذه التعديلات، لا تعدّل النظام عشوائيًا لإسكاته.

صنّفه:

* SEO regression
* performance regression
* build failure
* database/schema failure
* unrelated pre-existing failure

لكن حاول إصلاح أي مشكلة حقيقية ناتجة عن تعديلاتك.

"تم إصلاح favicon"
أو
"SEO Gate PASS".

SEO + favicon + canonical + dynamic URL + Hero/LCP + mobile performance + PHP + SQLite + sitemap + archive.
