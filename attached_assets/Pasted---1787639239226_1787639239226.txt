# 2. CUSTOMER → CONTRACT

من الواجهة:

1. إنشاء Customer جديد.
2. إنشاء Site.
3. إنشاء/اختيار Container.
4. إنشاء Contract.
5. تحقق أن العقد مرتبط فعليًا بالعميل والموقع والحاوية.

ثم أعد نفس إنشاء العقد بنفس `Idempotency-Key`.

المطلوب:

```text
First → Created
Second → Same Contract
No Duplicate
```

---

# 3. CONTRACT → WORK ORDER

عند تجهيز العقد:

**يجب إنشاء Work Order وليس Service Request جديدًا.**

اختبر:

```text
Delivery
Pickup / Return
Emptying
```

وتحقق بعد كل عملية من:

```text
service_requests
work_orders
appointments
container state
contract state
```

المطلوب ألا تُنشأ Service Request تشغيلية جديدة.

# 7. EMPTYING

هذه نقطة حرجة جدًا.

نفذ Emptying منفصلًا.

يجب أن يبقى:

```text
Emptying = Operational Work Order
```

ولا يتم معاملته كـDelivery.

لا تسمح لأي كود أن يغير:

```text
Contract → delivered
Container → rented
```

بشكل خاطئ نتيجة عملية Emptying.

# 8. AUTOMATIC INVOICE

هذه أهم نقطة في الاختبار المالي.

بعد إنشاء العقد، تحقق من أن النظام أنشأ الفاتورة تلقائيًا.

لا تنشئ فاتورة يدويًا إذا كان العقد يجب أن يولدها تلقائيًا.

يجب أن تكون:

```text
Contract
→ Invoice
```

مرتبطة بـ:

```text
Customer
Contract
Container
Billing Period
Amount
```

وتظهر في:

```text

```

### Contract Profile

```text
Invoice
```

```text

```

# 11. PARTIAL PAYMENT

إذا كانت الفاتورة:

```text
1000
```

نفذ:

```text
Payment #1 = 500
```

يجب أن تصبح:

```text
Paid = 500
Remaining = 500
Status = partially_paid
```

ثم:

```text
Payment #2 = 100
```

يجب أن تصبح:

```text
Paid = 600
Remaining = 400
Status = partially_paid
```

**يجب ألا تصبح 1200.**

هذه المشكلة ظهرت سابقًا وتم إصلاحها، لذلك يجب إثباتها Live وليس Local فقط.
