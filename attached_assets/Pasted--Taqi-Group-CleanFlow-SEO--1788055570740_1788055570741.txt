# 3 — وحّد شروط indexability

هذه نقطة حرجة.

التدقيق السابق أثبت:

* Posts: prerender يعتمد published + active.
* SEO pages: published + active.
* Services: prerender كان يعتمد active فقط.
* Containers/packages: prerender كان يعتمد active فقط.
* Sitemap للخدمات والحاويات يعتمد أيضًا `seoEnabled`.

هذا غير مقبول.

يجب أن يكون هناك **مصدر منطقي موحد لتعريف الصفحة القابلة للفهرسة**.

أي service/package لا يحقق شروط indexability يجب ألا يحصل على:

* canonical indexable
* sitemap entry
* indexable prerender HTML

والـlegacy aliases تظل:

`noindex, follow`

ولا تدخل sitemap.

لا تصلح هذه النقطة بتعديل الـDashboard. أصلح query/filter نفسه.

# 4 — وحّد Node وPHP فعليًا

لا أريد «Node وPHP يعرضان نفس الرقم».

أريد نفس **القواعد**.

راجع:

* slug generation
* description normalization
* title normalization
* keyword normalization
* canonical generation
* entity path
* Arabic slug
* ID-appended slug
* aliases
* noindex behavior
* sitemap filtering
* published/active/seoEnabled conditions
* custom SEO fields.

التقرير السابق أثبت أن Node وPHP لديهما فروقات حقيقية، ومنها اختلافات في slug generation/resolution، وأن PHP يستخدم `LIKE ... LIMIT 1` في بعض مسارات resolution، وهذا قد يؤدي إلى نتيجة غامضة إذا كانت البيانات متقاربة.

لا تترك ذلك كما هو.

إذا كان هناك helper واحد يمكن جعله authoritative، اجعله كذلك.

إذا كان PHP يجب أن يطابق Node بسبب Hostinger، فاجعل algorithm متطابقًا، وليس فقط output الحالي متطابقًا.

# 5 — أصلح الـslug architecture

هذه ليست مهمة تجميلية.

التقرير أثبت أن service/package SEO slugs لا يوجد عليها DB uniqueness constraint، وأن uniqueness الحالية application-level فقط، وبالتالي هناك race condition محتملة في concurrent writes.

راجع:

* schema
* migrations
* create
* update
* backfill
* Node
* PHP
* public resolver
* prerender
* sitemap.

المطلوب:

* لا duplicate canonical slugs.
* لا empty SEO slugs للصفحات indexable.
* slug ثابت بعد الإنشاء إلا إذا طلب المستخدم تغييره.
* update للمحتوى لا يغيّر slug بدون سبب.
* custom SEO slug يحترم uniqueness.
* collision handling deterministic.
* لا يوجد resolver غامض يعيد أول row بسبب `LIKE`.
* Arabic + ID alias يجب أن يحل إلى الكيان الصحيح تحديدًا.
* Node وPHP يجب أن يستخدما نفس canonical identity.

إذا احتاجت DB constraint/migration، نفذها بالطريقة الآمنة المناسبة للمشروع.

**لا تكسر البيانات الحالية.**

قبل أي migration destructive اعمل backup/working copy وتحقق من duplicates أولًا.

---

# 6 — أوقف الكتابة الخطرة أثناء PHP requests

هذه من أهم النقاط التي لا أريد أن يتم تجاهلها.

التدقيق السابق أثبت أن `api-index.php` ينفذ migrations و`seoAutoBackfill()` أثناء الطلبات، وأن backfill قد يعدّل بيانات الـcontent والـslug.

هذا خطر لأن:

PHP request
→ يغير DB
→ slug يتغير
→ prerender القديم يصبح stale
→ sitemap القديم يصبح stale
→ canonical HTML القديم يصبح stale.

هذا ليس production architecture سليم.

المطلوب:

* migrations تكون startup/deployment operation وليست كل request.
* backfill لا يغير authoritative slugs أثناء public request.
* إذا كان backfill مطلوبًا، اجعله explicit build/migration step.
* public request يجب أن يكون deterministic read path.
* لا تجعل أول crawler request يغيّر SEO database.

إذا كان Hostinger يحتاج compatibility behavior، صممه بدون mutation على كل request.

# 26 — والأهم: لا تكرر أخطاء الـagents السابقين

التقرير السابق نفسه أثبت أن هناك فرقًا بين ما كان "proven" وما كان مجرد claim. مثلًا لم يكن قد تم إثبات production HTTP behavior أو deployed Hostinger contents أو crawler behavior في ذلك التدقيق.

لذلك في التقرير النهائي صنّف كل نتيجة:

* `VERIFIED`
* `PARTIALLY VERIFIED`
* `NOT VERIFIED`

ولا تكتب PASS إذا لم تستطع إثباتها.
