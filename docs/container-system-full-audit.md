# التدقيق التشغيلي الكامل لنظام الحاويات

الحالة: Phase 0 — Discovery & Audit  
تاريخ التدقيق: 2026-08-22  
نطاق التدقيق: `CleanFlow Services`، نظام الإدارة، API الخاص بنظام الحاويات، قاعدة بيانات سجلات الحاويات، وكتالوج الباقات.

## 1. نتيجة التدقيق التنفيذية

النظام ليس CRUD وهمياً. توجد قواعد خلفية فعلية للربط والتحقق ومزامنة حالة الحاوية والتدقيق والحسابات. لكن الواجهة لا تزال في مواضع كثيرة تعرض العملية كـ "سجل عام" بدلاً من عرضها كسير عمل تشغيلي.

القرار المعماري:

1. الاحتفاظ بنواة API الحالية وقواعد التحقق التي أثبتت صحتها.
2. عدم توسيع `RecordDialog` ليصبح حلاً لكل العمليات.
3. تحويل العمليات الأساسية إلى Workspaces/Wizards/Field workflows حسب طبيعتها.
4. إبقاء `Packages` ككتالوج عرض وتسويق منفصل عن أصول الحاويات الفعلية.
5. عدم بدء إعادة التصميم البصري قبل تثبيت دورة العمل والحالات والعلاقات.

التقييم الحالي:

| الغرض التجاري | 6/10 | موجود لكنه غير ظاهر من بنية الشاشة |

## 3. دورة العمل المستخرجة من النظام الحالي

الدورة الحالية الفعلية، وليست الدورة المقترحة فقط:

```text
Service Request
  └─(requestId اختياري)
      Customer
        └─ Contract
            ├─ Container asset
            ├─ Contract value + tax + total
            ├─ Request link + customerRecordId + containerRecordId
            └─ Contract action
                 ├─ deliver → create container_movement → rented
                 ├─ return  → create container_movement → available
                 ├─ settle  → settled
                 ├─ debt    → delinquent
                 └─ close   → closed

Container movement
  ├─ validates containerCode
  ├─ validates movementType
  ├─ validates current asset status
  ├─ validates optional coordinates
  ├─ syncs asset status/location
  └─ writes audit movement_sync

Contract / Invoice
  └─ Payment or Receipt
       └─ automatic ledger_entry

Expense / Deposit / Bank deposit
  └─ automatic ledger_entry
```

### فجوات الدورة الحالية

1. لا يوجد كيان Work Order مستقل في مسار نظام الحاويات، رغم أن أوامر العمل موجودة في نظام الإدارة العام.
2. `appointment` سجل منفصل وليس جزءاً من مهمة تشغيلية.
3. إجراء العقد `deliver` ينشئ حركة تلقائية ببيانات محدودة، وقد يفشل بعد تحديث العقد؛ هذا يحتاج عملية ذرية أو workflow تعويضي واضح.
4. لا يوجد مسار صريح: `Scheduled → Assigned → En route → Arrived → Evidence → Completed`.
5. لا توجد عملية تسوية مالية متكاملة؛ توجد أرقام مشتقة من السجلات.
6. لا توجد Idempotency key ظاهرة للعمليات المالية أو حركات العقد.
7. الاعتماد على `customerName` و`contractNumber` و`containerCode` يظل جزئياً بدلاً من علاقات ID كاملة.

## 4. مصفوفة الحالات والانتقالات

### 4.1 الحاوية

الحالات المدعومة أو الظاهرة:

| الحالة | معناها | انتقال صحيح حالياً | المالك المقترح |
|---|---|---|---|
| `available` | جاهزة للتخصيص | delivery/reserve/inspection | التشغيل |
| `reserved` | محجوزة لعقد/موعد | assign أو release | المشرف |
| `rented` | لدى عميل | replacement/unloading/return | التشغيل |
| `in_transit` | في حركة | return/arrival/next movement | السائق/المشرف |
| `inspection` | تحت الفحص | available/maintenance/damaged | المشرف |
| `maintenance` | في الصيانة | inspection/available | مدير الأسطول |
| `damaged` | تالفة | maintenance/out_of_service | مدير الأسطول |
| `lost` | مفقودة | investigation/closed | الإدارة |
| `out_of_service` | خارج الخدمة | inspection بعد الإصلاح | مدير الأسطول |

مشكلة حالية: النظام يستخدم `rented` للحاوية، بينما `with_customer` و`awaiting_return` تظهر أيضاً في خيارات الواجهة. يجب اعتماد آلة حالات واحدة وعدم السماح للمستخدم باختيار حالة عشوائية من قائمة عامة.

### 4.2 العقد

| الحالة | الاستخدام الحالي | القرار |
|---|---|---|
| `draft` | مسودة | تبقى |
| `active` | نشط | يجب فصلها عن approved |
| `issued` | صادر | تبقى كحالة مستند |
| `scheduled` | مجدول | يجب أن ترتبط بموعد/مهمة |
| `delivered` | تم التسليم | يجب أن تكون نتيجة حركة مثبتة |
| `settled` | مصفى | يجب تعريف التصفية مالياً |
| `delinquent` | مديونية | يجب أن تنشأ من كشف حساب |
| `closed` | مغلق | يجب منع الحركات الجديدة إلا بتصحيح |
| `archived` | مؤرشف | تاريخي غير قابل للحذف |

الفجوة: لا توجد حالتا `pending_approval` و`approved` كمسار اعتماد واضح، رغم وجود حد أدنى وموافقة استثناء.

### 4.3 الحركة

الأنواع المدعومة:

`delivery`, `replacement`, `swap`, `unloading`, `emptying`, `withdrawal`, `return`, `maintenance`.

المشكلة: النوع مخزن في حقل نصي، بينما يجب أن يكون Action محدداً حسب الحالة الحالية والعقد والمهمة.

### 4.4 المال

الدورة المطلوبة:

```text
Contracted → Invoiced → Due → Collected → Deposited → Reconciled
Expense → Approved → Paid → Posted
Revenue - Cost → Profitability
```

الدورة الحالية تحقق جزءاً من `Collected` و`Posted` فقط، ولا تملك مراحل اعتماد وتسوية رسمية.

## 5. مصفوفة العلاقات

| العلاقة | الحالية | النوع الصحيح | المالك | قرار |
|---|---|---|---|---|
| العميل ← العقد | اسم + customerRecordId | One-to-Many | العميل/العقد | إلزام ID |
| العميل ← الموقع | غير موجود ككيان | One-to-Many | العميل | إضافة Sites |
| العقد ← الحاوية | containerCode + containerRecordId | Many-to-Many محتملة | العقد/التخصيص | كيان Assignment |
| العقد ← البنود | contract_line منفصل | One-to-Many | العقد | تعريف Rental/Line |
| العقد ← الحركة | contractNumber | One-to-Many | العقد | إلزام contractId |
| الحركة ← الحاوية | containerCode | Many-to-One | الأصل | إلزام assetId |
| الحركة ← السائق | driverName | Many-to-One | المهمة | إلزام driverId |
| الحركة ← الشاحنة | vehiclePlate | Many-to-One | المهمة | إلزام vehicleId |
| الموعد ← المهمة | غير مكتمل | One-to-One/One-to-Many | أمر العمل | دمج appointment في dispatch |
| العقد ← الفاتورة | contractNumber | One-to-Many | المالية | إلزام contractId |
| الفاتورة ← التحصيل | invoiceNumber | One-to-Many | المالية | إلزام invoiceId |
| الحركة ← الأثر المالي | غير رسمي | Zero-to-Many | المالية | Event/ledger source |
| الحاوية ← الصيانة | vehicle-style records فقط | One-to-Many | الأصل | إضافة assetId |

## 6. التدقيق التفصيلي للنوافذ الحالية

### 6.1 نافذة RecordDialog العامة

**Current State:** Dialog واحد يولّد الحقول من `FIELD_CONFIG` لكل أنواع السجلات.

**تستخدم حالياً لـ:**

- عميل.
- نوع حاوية.
- أصل حاوية.
- عقد.
- إيجار.
- حركة.
- سيارة.
- سائق.
- صيانة.
- تصريح.
- موعد.
- مالية.
- مخزون.
- إعدادات.

**المشكلة:** نفس بنية "البيانات الأساسية + الحالة + حفظ" تُستخدم لعمليات تختلف في المخاطر والآثار.

**الحقول العامة المستخرجة:**

| مجموعة الحقول | أمثلة | القرار |
|---|---|---|
| Identifiers | requestId، customerRecordId، containerRecordId، contractNumber | تقني؛ لا تظهر للمستخدم، يشتقها النظام |
| Business references | customerName، containerCode، vehiclePlate | تتحول إلى اختيار سياقي يعرض الحالة |
| Dates | startDate، endDate، movementDate، appointmentDate | تتحقق حسب العملية والمنطقة الزمنية |
| Money | amount، taxRate، taxAmount، total، cost | amount وtaxRate يدخلان، الباقي يحسب |
| State | status | لا يختار من قائمة عامة؛ الانتقال يحدده workflow |
| Evidence | proofPhotoUrl، signatureData | رفع صورة/توقيع فعلي، لا URL نصي |
| Notes | notes، description | تبقى لكن تكون مرتبطة بسبب/قرار |

**الأزرار الحالية:**

| الزر | السلوك الحالي | الحكم |
|---|---|---|
| إلغاء | يغلق النافذة | صحيح، يحتاج تحذير إذا توجد تغييرات |
| حفظ السجل | POST/PATCH عام | يجب استبداله بأفعال دلالية |
| مسح التوقيع | يمسح canvas | صحيح، يحتاج تأكيداً قبل فقدان توقيع موجود |
| اختيار قالب العقد | يكتب الشروط في notes | جيد كبداية، يجب ألا يستبدل شروطاً معدلة دون تحذير |

**قرار:** الإبقاء عليه فقط للسجلات الإدارية البسيطة:

- نوع حاوية.
- إعداد بسيط.
- فرع.
- تصنيف.

ويزال من:

- العقود.
- الحركات.
- المواعيد.
- المالية.
- التخصيص.

### 6.2 نافذة تفاصيل السجل

**Current State:** تعرض payload كشبكة حقول، مع أزرار ملف العميل/الموظف/الحاوية وطباعة العقد وإجراءات دورة العقد.

**المشكلة:**

- تعرض مفاتيح البيانات أكثر مما تعرض قراراً.
- إجراءات العقد تغيّر الحالة مباشرة.
- التسليم والاسترجاع ينشئان حركة لاحقاً في Mutation منفصلة.
- فشل مزامنة الحركة قد يترك العقد محدثاً والحركة غير مكتملة.
- ربحية العميل تعتمد على مطابقة الاسم/رقم العقد.

**الأزرار التي يجب فصلها:**

- فتح الملف: يبقى.
- طباعة العقد: يبقى كإخراج.
- تسجيل التسليم: يتحول إلى Delivery workflow.
- تسجيل الاسترجاع: يتحول إلى Return/Pickup workflow.
- تصفية العقد: تتحول إلى Settlement screen.
- تحويل لمديونية: Approval/Collection workflow.
- إغلاق العقد: Confirmation مع شروط الإغلاق.

### 6.3 نافذة إنشاء العميل

**الهدف الصحيح:** إنشاء طرف تجاري يمكن استخدامه في العقود والتحصيل والطلبات.

**الحقول الحالية:**

| الحقل | القرار |
|---|---|
| الاسم | مطلوب، بشري/تجاري |
| الجوال | مطلوب للعميل الفردي، اختياري مع سبب للشركة |
| المدينة | اختيار من قائمة/منطقة |
| الرقم الضريبي | يظهر للشركة أو عند اختيار نوع العميل |
| الملاحظات | اختيارية، لا تستخدم لعلاقات |

**يجب إضافته:**

- نوع العميل.
- رقم العميل.
- البريد.
- مواقع العميل.
- ممثل العميل.
- الحد الائتماني.
- حالة الحساب.

**يجب أن يحدث بعد الحفظ:** يظهر العميل كخيار سياقي، وتظهر حالته ورصيده وعقوده عند اختياره.

### 6.4 إنشاء العقد

**Current State:** نافذة عامة تحتوي على معرفات وحقول متكررة.

**القرار:** تتحول إلى Wizard كامل من 8–12 خطوة:

1. العميل.
2. الموقع.
3. نوع العقد.
4. الخدمة.
5. الحاوية/الحاويات.
6. المدة أو الرحلات.
7. السعر والضريبة.
8. الشروط والاستثناء.
9. المراجعة.
10. الاعتماد.
11. الإصدار.
12. إنشاء أول مهمة.

**معيار القبول:** لا يستطيع المستخدم إصدار عقد نشط دون عميل صحيح، موقع، حاوية متاحة، تواريخ صحيحة، تسعير، حالة اعتماد، وإظهار أثر الإصدار.

### 6.5 حركة الحاوية

**Current State:** RecordDialog بحقول `movementType`, `containerCode`, `vehiclePlate`, `driverName`, coordinates, proofPhotoUrl, receiverName.

**القرار:** تتحول إلى Mobile/Field workflow.

**ما يظهر للسائق:**

- المهمة الحالية.
- العميل.
- الموقع.
- الحاوية.
- العقد.
- الشاحنة.
- الخطوة التالية.

**ما لا يظهر للسائق كحقول تقنية:**

- Latitude.
- Longitude.
- Image URL.
- IDs.
- حالة عامة قابلة للاختيار.

**الأفعال:**

```text
ابدأ المهمة
→ في الطريق
→ وصلت
→ تأكيد الموقع
→ صورة
→ توقيع/إثبات
→ تم التسليم أو الاستلام
→ مزامنة الحالة
→ إنهاء المهمة
```

**معيار القبول:** الضغط المتكرر لا ينشئ حركة ثانية، وفشل رفع الدليل لا يعلن اكتمال العملية، وتظهر حالة الحاوية والعقد والمهمة بعد النجاح.

### 6.6 ملف الحاوية

**Current State:** يعرض الحالة والموقع وعدد الحركات والعقود وقائمتين مرتبطتين.

**القرار:** Container 360 Workspace.

**يجب أن يحتوي على:**

- هوية الأصل.
- النوع والحجم والصور والفرع والملكية.
- الموقع الحالي وآخر موقع معروف.
- العميل والعقد الحاليان.
- Timeline كامل.
- المهمة القادمة.
- آخر فحص وصيانة.
- التكلفة والإيراد وأيام التأجير والاستغلال.
- الأضرار والخسائر.
- إجراءات مسموحة حسب الحالة.

**الأزرار:**

- تعيين.
- حجز.
- تسجيل تسليم.
- تسجيل تبديل.
- طلب سحب.
- تسجيل استرجاع.
- إدخال صيانة.
- الإبلاغ عن تلف/فقد.
- فتح العقد.
- فتح كشف العميل.

### 6.7 البحث عن حاوية

**Current State:** يبحث في سجلات API ويعرض رقم الحاوية والعميل والهاتف وبداية ونهاية الإيجار والحالة.

**المشكلة:** البحث في payload نصياً، وليس بحثاً موحداً في أصل وعقد وعميل ومهمة.

**القرار:** الاحتفاظ بالبحث كمدخل سريع، مع نتائج موحدة:

- الأصل.
- آخر موقع.
- الحالة.
- العميل.
- العقد.
- آخر حركة.

## 13. سجل التنفيذ والتحقق — تحديث 2026-08-22

هذا القسم هو سجل الحالة التنفيذي للوثيقة. كلمة **مكتمل** تعني أن الكود والربط الخلفي والواجهة موجودة، وليس أنها اجتازت تجربة مستخدم مصادق عليها في بيئة الإنتاج.

### 13.1 مكتمل في الكود

| المجال | ما تم تنفيذه | معيار القبول المرتبط |
|---|---|---|
| ترقيم المستندات | توليد أرقام العقود `RNT-YYYY-######` والفواتير `INV-YYYY-######` من الخادم بعد إنشاء السجل، مع حفظ الرقم في `reference` وداخل `payload` | الرقم لا يعتمد على إدخال المستخدم ويظل قابلاً للبحث والطباعة |
| العقد التشغيلي | معالج متعدد الخطوات يختار العميل والأصل والموقع، يتحقق من الفترة والسعر والضريبة، ويعرض المراجعة قبل الإصدار | منع العقد النشط دون عميل وموقع وأصل وفترة وقيمة |
| التخصيص | معالج سياقي يختار العقد ثم مواقع العميل التابعة له ثم الأصل المتاح، مع منع التخصيص النشط المكرر | عدم إدخال `customerRecordId` أو `containerRecordId` يدوياً |
| ربط العقد | إصدار العقد ينشئ التخصيص الرسمي تلقائياً قبل الموعد وأمر العمل، مع تحديث الأصل إلى `reserved` | اكتمال المسار `Customer → Site → Contract → Assignment` |
| الجدولة | إنشاء الموعد وأمر العمل مرتبطين بالعقد والعميل والأصل والموقع | ظهور العملية في تقويم التشغيل |
| أوامر العمل | حالات السائق المتتابعة: قبول، بدء، في الطريق، وصول، إكمال | منع الانتقال غير المسموح من الخادم |
| إثبات التنفيذ | اسم المستلم، صورة، توقيع، وإحداثيات اختيارية؛ فشل رفع الصورة يمنع الإكمال | لا تصبح حركة الحاوية مكتملة دون إثبات |
| التزامن | إعادة إرسال نفس الحالة لا ينشئ حركة أو أثراً إضافياً | الضغط المتكرر آمن |
| مزامنة الأصل | إكمال أمر التسليم أو الاسترجاع يحدّث العقد والأصل وينشئ حركة وسجل تدقيق داخل معاملة | عدم بقاء العقد محدثاً دون أثر الحركة |
| ملف الحاوية 360 | عرض الهوية، الحالة، الموقع، العقود، الحركات، أوامر العمل، والتاريخ الزمني | نقطة بداية تشغيلية لقصة الأصل |
| التسوية | كشف العقود، المحصل، المودع، المتبقي، ومنع التكرار بمفتاح عملية | ربط التحصيل بالعقد والقيد والإيداع |
| التقويم والتوزيع | إظهار أوامر العمل غير المسندة في تقويم المشرف حتى يمكن إسناد السائق والشاحنة من نفس الشاشة | لا يختفي الموعد قبل الإسناد |
| مؤشرات التوزيع | إظهار غير المسند، مواعيد اليوم، المتأخر، ونسبة الإسناد، مع تنبيه تعارض السائق في نفس اليوم | قرار تشغيلي سريع قبل بدء الجولة |
| حماية التعارض | فحص تعارض السائق والشاحنة على الخادم والواجهة حسب يوم الموعد، وليس فقط تطابق التوقيت النصي | منع تجاوز التعارض من عميل أو جلسة أخرى |
| الصلاحيات الأساسية | حماية مسارات السائق والمشرف والـAPI حسب الدور، ومنع تعديل الحركات بعد تسجيلها | الفشل بصلاحية واضحة بدلاً من تعديل صامت |

| المجال | الموجود الآن | ما ينقص قبل اعتباره مكتملاً |
|---|---|---|

| الاعتماد الإلكتروني | توقيع محفوظ ضمن نموذج العقد/الإكمال وطباعة A4، مع اعتماد/رفض عقد مسجل على الخادم وأثر تدقيق | نسخة إصدار غير قابلة للتغيير وربط توقيع الاعتماد نفسه بنسخة العقد |

### 13.3 نتيجة الاختبار الحقيقي الأخير

بحسب الاختبار التشغيلي الحقيقي المنفذ الآن، تم تأكيد التدفق الأساسي التالي من بدايته إلى نهايته:

1. إنشاء/اختيار العميل وربط الطلب به.
2. إنشاء العقد وربطه بالعميل والأصل والموقع.
3. إنشاء الطلب/أمر العمل وربطه بالعقد عند الحاجة.
4. إسناد الطلب إلى السائق من شاشة المشرف.
5. ظهور الطلب في حساب السائق المسند إليه فقط.
6. تنفيذ حالات السائق بالتتابع: قبول، بدء، في الطريق، وصول.
7. تسجيل بيانات التسليم/الإكمال: اسم المستلم، الموقع عند توفره، صورة الإثبات، والتوقيع.
8. إكمال المهمة، ثم انعكاس النتيجة على الطلب والعقد والأصل والحركة وسجل التدقيق.

**حالة هذا التدفق:** ناجح في الاختبار الحقيقي الذي أجراه المستخدم، بما في ذلك رفع صورة الإثبات من حساب السائق بعد إصلاح مسار الرفع المحمي. لا يعني ذلك أن كل متطلبات الجاهزية الإنتاجية أو كل مسارات الاستثناء قد أُغلقت.

تبقى الاختبارات التالية مطلوبة لإغلاق الاعتماد الإنتاجي الكامل:

1. إعادة الإرسال بعد انقطاع الشبكة في كل خطوة، وليس الإكمال فقط، من جهاز جوال فعلي.
2. تنفيذ استرجاع حاوية مستقل والتأكد من انعكاس الحالة في العقد والأصل وملف Container 360 والتدقيق.
3. فشل رفع الصورة، ورفض إذن الموقع، ورفع ملف غير مسموح، والتأكد من بقاء المهمة غير مكتملة وعدم ترك أثر مضلل.
4. اختبار التعارض عند إسناد سائق أو شاحنة إلى مهمتين في اليوم نفسه من جلستين مختلفتين.
5. تجربة الأدوار `admin`, `manager`, `customer_service`, `requests_officer`, و`driver` على كل إجراء، لا على تسجيل الدخول فقط.
6. تسجيل تحصيلين بنفس مفتاح العملية والتأكد من وجود أثر مالي واحد فقط.
7. بناء أرشيف Hostinger وتشغيل نسخة PHP/SQLite مستقلة والتحقق من أن الترقيم والتدقيق لا يعتمدان على Node أو خدمة Replit.

| غير مسندة | أمر مرتبط بعقد أو مسار `contract_workflow`، حالته التشغيلية `unassigned`، وليس مكتملًا أو مرفوضًا | `service_requests.assigned_driver_id`, `driver_status`, `contract_record_id`, `acquisition_source` | يظهر في شاشة أوامر العمل للمشرف |
| مواعيد اليوم | أوامر لها `scheduled_at` يقع في تاريخ اليوم المحلي | `service_requests.scheduled_at` | لا يعني أن المهمة بدأت أو اكتملت |
| متأخرة | موعد مضى، والحالة ليست `completed` أو `rejected` | `service_requests.scheduled_at`, `driver_status` | مؤشر تنبيه تشغيلي وليس حكم SLA نهائيًا |
| نسبة الإسناد | عدد الأوامر التي لها سائق مسند ÷ إجمالي الأوامر المعروضة × 100 | `assigned_driver_id` | تُعرض كنسبة تقريبية في لوحة التوزيع |
| الاستفادة التقديرية للأصل | أيام العقود المحسوبة ÷ الحد المرجعي المقدر للعقود، مع سقف 100% | عقود الأصل: `startDate`, `endDate` | مؤشر تحليلي تقديري، وليس قراءة عداد تشغيل |
| صافي قيمة الأصل | الإيرادات المرتبطة − المصروفات − تكلفة الصيانة | سجلات `payment`, `receipt`, `invoice`, `expense`, `maintenance` | لا يشمل تكلفة الشراء أو الإهلاك لعدم وجود مصدر محاسبي لها بعد |

### 13.7 تحديث تنفيذ 2026-08-22

- أُضيف فحص تعارض الخادم للسائق والشاحنة في نفس يوم الموعد، بحيث لا يمكن تجاوز الحماية بإرسال طلب مباشر أو من جلسة أخرى.
- أُضيف الفحص نفسه في واجهة التوزيع قبل الإرسال لتقديم رسالة فورية للمشرف.
- أُضيفت دورة اعتماد العقد `pending_approval → approved/rejected` بصلاحية المدير أو المدير الرئيسي، مع وقت ومعرّف المعتمد وسجل تدقيق.
- تم توثيق مصادر مؤشرات التوزيع وContainer 360 بدل تركها كمؤشرات وصفية بلا تعريف.
- تبقى موافقة الإنتاج الكاملة واختبارات الاستثناء والصلاحيات بحسابات تشغيلية مفتوحة كما هو موضح في القسم 13.3؛ لا تُحوّل الإضافة البرمجية وحدها إلى اعتماد ميداني.

### 13.8 تحديث تنفيذ 2026-08-22 — سياق إجراءات ملف العميل

- أُغلقت فجوة الإجراءات السريعة في ملف العميل: الانتقال إلى إنشاء العقد أو إضافة موقع يمرر `customerId` في المسار.
- يبدأ معالج العقد بالعميل المحدد تلقائيًا، ويبدأ نموذج الموقع بمعرّف العميل المحدد دون إدخال تقني يدوي.
- تبقى إجراءات التسوية مرتبطة بالعميل عبر مسار التسوية، بينما يظل اعتمادها النهائي واختبارها بحسابات تشغيلية فعلية ضمن قائمة التحقق الميداني.

### 13.9 تحديث تنفيذ 2026-08-22 — التسوية والتحقق المباشر

- أصبحت شاشة تسوية العقود تقبل `customerId` من ملف العميل، وتعرض عقود ذلك العميل فقط وتحدد أول كشف مستحق تلقائيًا.
- تم التحقق من المشروع كاملًا عبر فحص الأنواع، ومن صحة خادم API عبر `/api/healthz`.
- مسار التسليم والاسترجاع الذري وإنشاء العقد الأولي محميان بمعاملة خادمية واحدة؛ إنشاء العقد يقبل مفتاح عملية ويعيد النتيجة السابقة عند إعادة الإرسال بدل إنشاء سجلات مكررة.
- تم اختبار مسار السائق الحقيقي ضمن التدفق الأساسي، لكن ذلك لا يغطي مصفوفة الصلاحيات كاملة ولا يجعل النظام مقبولاً إنتاجياً قبل إغلاق اختبارات الاستثناء والاسترجاع والمالية ونسخة Hostinger الواردة في القسم 13.3.
- أصبحت انتقالات السائق من القبول حتى الإكمال ترسل مفتاح عملية ثابتاً لكل أمر وحالة، ويعيد الخادم النتيجة السابقة عند تكرار الإرسال بدلاً من إنشاء حركة أو سجل تدقيق إضافي.

### 13.10 تحديث تنفيذ 2026-08-22 — اعتماد تدفق العقد والطلب والتسليم والإكمال

تمت مراجعة التدفق بعد الاختبار الحقيقي وتثبيت التسلسل التشغيلي المعتمد:

```text
Customer/Site
  → Contract
  → Service Request / Work Order
  → Driver Assignment
  → Accepted
  → Started
  → En route
  → Arrived
  → Evidence
  → Completed
  → Contract + Container + Movement + Audit
```

#### ما تم تأكيده

| المرحلة | النتيجة | دليل النجاح |
|---|---|---|
| العقد | ناجح | العقد مرتبط بالعميل والأصل والموقع وقابل للمتابعة |
| الطلب | ناجح | الطلب يتحول إلى أمر عمل قابل للإسناد |
| الإسناد | ناجح | يظهر الطلب للسائق المرتبط به فقط |
| التسليم الميداني | ناجح | السائق يمر بالحالات المتتابعة ويسجل بيانات المستلم |
| الإثبات | ناجح | صورة الإثبات والتوقيع يمران عبر مسار محمي للسائق |
| الإكمال | ناجح | لا يتم الإكمال عند غياب الإثبات المطلوب، وتُحفظ الآثار المرتبطة داخل معاملة |
| التدقيق | موجود | انتقال الحالة يسجل قبل/بعد والفاعل |

#### ما لا يزال ناقصاً رغم نجاح التدفق الأساسي

1. **تسوية الملفات المرفوعة:** إذا نجح رفع الصورة ثم فشل حفظ الإكمال، قد يبقى ملف غير مرتبط؛ يلزم تنظيف أو ربط مؤجل واضح.
2. **طابور مزامنة ميداني:** لا توجد بعد آلية Offline Queue حقيقية تحفظ العمليات عند انقطاع الشبكة ثم تعيد إرسالها بأمان.
3. **إشعار موحد للتدفق:** إسناد المهمة موجود، لكن يلزم توثيق إشعارات كل انتقال وفشل وتغيير موعد وربطها بصندوق السائق والمشرف.
4. **إثبات التسليم كنسخة غير قابلة للتغيير:** الصورة والتوقيع محفوظان، لكن يلزم تثبيت نسخة دليل مرتبطة بإصدار العملية ووقت الخادم.
5. **اختبار الاسترجاع والعمليات البديلة:** التسليم ليس بديلاً عن اختبار الاسترجاع، التبديل، السحب، التفريغ، والتصحيح التشغيلي.
6. **التسوية المالية النهائية:** نجاح الإكمال لا يثبت أن الفاتورة والتحصيل والإيداع والتسوية والربحية دورة واحدة مكتملة.
7. **اختبارات آلية للتدفق:** يلزم تحويل المسار الناجح ومسارات الرفض والتكرار إلى اختبارات API/واجهة قابلة لإعادة التشغيل.

### 13.11 الحكم الحالي بعد الاختبار

**التدفق الأساسي للعقد → الطلب → الإسناد → التسليم → الإثبات → الإكمال يعمل فعلياً ومكتمل وظيفياً للنطاق الذي تم اختباره.**

لكن النظام ككل **ليس مكتملاً إنتاجياً بعد**؛ الإغلاق النهائي يتطلب إتمام النواقص السبعة أعلاه، واختبار الاسترجاع والصلاحيات والتسوية المالية ونسخة Hostinger، ثم إرفاق نتائج قابلة للتتبع لكل اختبار.
