# خطة صيانة وتقسيم نظام الحاويات

## 1. الوضع بعد تصفير بيانات التجربة

- تم حذف العقود التجريبية الحالية وكل ما ارتبط بها من:
  - بنود العقود.
  - تخصيصات الحاويات.
  - الحركات التشغيلية.
  - المواعيد الناتجة عن العقود.
  - الفواتير والدفعات والقيود المرتبطة بأرقام العقود المحذوفة.
- بقيت سجلات العملاء ومواقعهم وأنواع الحاويات وتعريفات الأصول.
- أُعيدت الحاويات التي كانت مرتبطة بالعقود إلى حالة `available`.
- توجد نسخة احتياطية قبل التصفير داخل مجلد البيانات، ولا تُستخدم كقاعدة تشغيلية.

## 2. ما يجب أن يظهر في صفحة العميل

### حالة التنفيذ الحالية

تم تنفيذ النسخة الأولى من ملف العميل: المؤشرات المالية، المواقع، الحاويات المخصصة، العقود، المواعيد، وأوامر العمل تظهر من السجلات الحالية. الإجراءات السريعة تفتح الآن مسار العقد أو الموقع أو التسوية مع تمرير العميل المحدد، وتعرض شاشة التسوية عقود ذلك العميل وتحدد أول عقد مستحق تلقائيًا.

صفحة العميل يجب أن تكون ملفًا تشغيليًا واحدًا، لا نسخة من شاشة العقود. تقسم إلى:

### الهوية والبيانات الأساسية

- اسم العميل التجاري والاسم المختصر.
- رقم الجوال والبريد.
- الرقم الضريبي والسجل التجاري عند توفرهما.
- نوع العميل وحالته ومصدره.
- بيانات التواصل المفضلة وملاحظات خدمة العملاء.

### المواقع

- قائمة المواقع المرتبطة بالعميل.
- العنوان والوصف وإحداثيات الموقع.
- اسم مسؤول الموقع ورقم التواصل.
- حالة الموقع وملاحظات الدخول أو التصاريح.
- زر إضافة موقع وتعديله دون مغادرة ملف العميل.

### ملخص تشغيلي

- عدد العقود النشطة والمنتهية والمعلقة.
- عدد الحاويات الحالية لدى العميل.
- أقرب موعد قادم.
- آخر حركة تشغيلية.
- إجمالي الفواتير، المدفوع، والمبلغ المستحق.
- حالة التسوية، مع رابط مباشر إلى التفاصيل المالية.

### سجل العميل

- العقود المرتبطة بالعميل مع حالتها ودورتها.
- التخصيصات والحاويات الحالية.
- المواعيد وأوامر العمل.
- الحركات والإثباتات والصور والتوقيعات.
- الصيانة أو البلاغات المرتبطة بالأصول الموجودة لدى العميل.
- سجل التدقيق المرتبط بالعميل، بصلاحية مناسبة.

### إجراءات سريعة

- إنشاء عقد جديد والعميل محدد مسبقًا.
- إضافة موقع.
- طلب استرجاع أو تسليم.
- تسجيل دفعة أو فتح كشف الحساب.
- طباعة ملخص العميل.

يجب أن تعتمد الصفحة على API-backed queries، وألا تجمع البيانات من `localStorage` أو من نسخ محلية غير موثوقة.

## 3. تقسيم `ContainerSystem.tsx`

### حالة التنفيذ الحالية

تم تحويل مسار إنشاء العقد إلى endpoint خادمي ذري: العقد والتخصيص والموعد وأمر العمل تُنشأ داخل معاملة واحدة، ويعاد نفس الناتج عند إعادة إرسال مفتاح العملية. لم تعد الواجهة تعتمد على أرشفة سجلات جزئية للتعويض.

كما تم ربط إجراءات ملف العميل بسياق العميل عبر معاملات المسار؛ إنشاء العقد وإضافة الموقع يبدآن بالعميل المحدد مسبقًا.

الهدف هو تقليل الملف الرئيسي إلى منسق صفحة، مع الحفاظ على نفس المسارات، مفاتيح العرض، أسماء السجلات، والتوكنز البصرية.

### المرحلة الأولى: تثبيت العقود الداخلية

1. استخراج الأنواع المشتركة إلى:
   - `container-system/types.ts`
2. استخراج ثوابت التنقل والأنواع إلى:
   - `container-system/navigation.ts`
3. استخراج دوال قراءة الحمولة والتسمية والمبالغ والحالات إلى:
   - `container-system/record-utils.ts`
4. عدم تغيير أسماء `ViewKey` أو `RecordKind` أو شكل الحمولة في هذه المرحلة.

### المرحلة الثانية: استخراج المكونات البصرية

1. `ContainerSidebar.tsx`
2. `ContainerSystemHeader.tsx`
3. `RecordDetailsDialog.tsx`
4. `ContainerSearchPanel.tsx`
5. `CustomerSummaryCard.tsx`
6. `ContractLifecycleActions.tsx`

كل مكون يستقبل بياناته ودواله عبر props، ولا ينشئ توكن مصادقة جديدًا.

### المرحلة الثالثة: استخراج مسارات الأعمال

1. `useContainerSystemRecords.ts`
   - القراءة، الفلاتر، وإبطال الاستعلامات.
2. `useContainerRecordMutations.ts`
   - الإنشاء والتحديث والأرشفة.
3. `useContractWorkflow.ts`
   - إنشاء العقد، التخصيص، الموعد، وأمر العمل.
4. `useContractLifecycle.ts`
   - الاعتماد والرفض والتسليم والاسترجاع.
5. `useCustomerProfile.ts`
   - تجميع العميل والمواقع والعقود والدفعات والحركات.

الـ hooks لا تحتوي JSX، وتستخدم نفس `admin_token` الحالي ونفس `API_BASE`.

### المرحلة الرابعة: فصل محتوى الصفحات المتخصصة

نقل واجهات العرض حسب المجال إلى:

- `views/OverviewView.tsx`
- `views/CustomersView.tsx`
- `views/ContractsView.tsx`
- `views/OperationsView.tsx`
- `views/FinanceView.tsx`
- `views/ReportsView.tsx`
- `views/SettingsView.tsx`

يبقى `ContainerSystem.tsx` مسؤولًا فقط عن اختيار العرض وتمرير السياق المشترك.

### المرحلة الخامسة: اختبار كل استخراج

بعد كل مرحلة:

- فحص TypeScript.
- فحص `git diff --check`.
- إعادة تشغيل واجهة الخدمات وخادم API عند تغيير مسار الأعمال.
- فتح صفحة الإدارة والتأكد من أن التوكن الحالي يمر كما هو.
- اختبار إنشاء عميل، إنشاء موقع، فتح ملف العميل، ثم إنشاء أول عقد تجريبي.
- اختبار منع التكرار والتعارض.

## 4. ترتيب التنفيذ المقترح

1. بناء صفحة ملف العميل أولًا باستخدام مكونات قراءة فقط.
2. استخراج الأنواع والثوابت والدوال المساعدة.
3. استخراج الحوار والتفاصيل والإجراءات.
4. استخراج mutations الخاصة بالعقد في hook مستقل.
5. التحقق الميداني من العملية الخادمية الذرية ومفتاح منع التكرار حتى لا تبقى سجلات جزئية.
6. فصل التقارير والمالية.
7. حذف الكود الميت بعد نجاح الاختبارات، وليس قبلها.

## 5. قواعد الحفاظ على التوكنز والأمان

- عدم تغيير `admin_token` أو طريقة قراءته في هذه الخطة.
- عدم وضع التوكن داخل props أو state أو ملفات المكونات.
- إبقاء طلبات الإدارة خلف نفس طبقة عميل API الحالية.
- عدم تغيير `API_BASE` أو المسارات الحالية أثناء الاستخراج.
- عدم نقل صلاحيات القرار إلى الواجهة؛ الخادم يبقى مصدر التحقق.
- أي تغيير في شكل payload يجب أن يمر عبر طبقة تطبيع واحدة واختبار توافق.

## 6. معيار اكتمال التقسيم

يُعتبر التقسيم مكتملًا عندما:

- يصبح الملف الرئيسي منسقًا صغيرًا بدل احتوائه على تفاصيل كل المجالات.
- يمكن تعديل دورة العقد دون لمس التقارير أو شاشة العملاء.
- يمكن تعديل ملف العميل دون لمس دورة التسوية.
- تمر فحوص الأنواع والبناء.
- تعمل جلسة الإدارة الحالية دون إعادة تسجيل دخول.
- لا تتغير نتائج API أو الصلاحيات أو سلوك المسارات الحالية.
